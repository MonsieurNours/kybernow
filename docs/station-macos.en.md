# KyberNow Station for Mac — scope

English · [Français](station-macos.md)

Scoped on 2026-11-03. This document sets the choices, the milestones and their status. What is planned lives in [ROADMAP.en.md](../ROADMAP.en.md).

## Goal

A Mac with Apple silicon becomes a Station like a Windows PC: same features, same Admin, same icon, and the KyberNow Link apps connect to it without (almost) knowing it is a Mac. For gaming (Steam for Mac, CrossOver, Game Porting Toolkit) as well as remote desktop, with the Game, Desktop and Max profiles.

## Status

**Milestone 1, in progress (2026-11-03)**: Kyber server built for Apple silicon with the Windows Station's 30 server patches, none changed (`server/macos/scripts/build-kyber.sh`, shared application in `server/kyber-patches/apply.sh`), started as a signed LaunchAgent by `server/macos/scripts/run-kyber.sh`. Tried on the M4 Max, locally with this Mac's Kyber client:

- the Mac's three displays found by ScreenCaptureKit, once Screen Recording is allowed for "KyberNow Station (Kyber)";
- HEVC picture through VideoToolbox (about 29 Mbit/s measured for 20 asked on a very busy screen, kyavserver at 3% CPU), stereo Opus sound at 256 kbit/s (output of the chosen display), keyframe on demand (0005);
- HEVC 4:4:4: the encoder opens (4:4:4 picture actually received: to check with a KyberNow app);
- H.264: refused by VideoToolbox on the main display (−12903), probably beyond 4,096 real pixels wide; the virtual display at the device's resolution will avoid it;
- `kVTCompressionPropertyKey_MaxFrameDelayCount` is not honoured by the HEVC encoder: VideoToolbox may hold frames back, to measure with latency;
- the Kyber client (VLC player) often runs short of sound samples: to revisit with the core's sound engine.

Left to finish the milestone: a picture on another device (KyberNow apps go through Admin, milestone 2; or the original Kyber client on the PC), end-to-end latency, input (kynputserver, Accessibility permission).

**Milestone 2, in progress (2026-11-03)**: Admin on Mac. `kyber-admin` recognises a Mac Station (Kyber's LaunchAgent), drives Kyber through launchd, announces itself with `kyber=1` under the Mac's name, gives its real network cards for wake, and `prepare` takes the Mac's display as it is (no virtual display or virtual sound before milestones 3 and 4); details in [server/README.en.md](../server/README.en.md#kybernow-station-for-mac-in-progress). Test Station: `server/macos/scripts/run-station.sh` (certificate of its own, accounts set by `kyber-admin init`). Checked on the M4 Max: Bonjour announcement, `info`, `prepare`, then a Kyber session with the account and fingerprint given by Admin; **picture received on the iPhone by the KyberNow app** (2026-11-03: the Mac's main display in HEVC, 70 Mbit/s asked, stereo Opus sound). Seen during this test: the first stream dropped after 4 s and the app restarted it ("Force IDR failed: Timeout" on Kyber's side), to understand; mouse and keyboard are refused by macOS (`CGPostMouseEvent` → 1002: no Accessibility permission, milestone 5); the home preview fails ("could not create image from display": Admin has no screen recording permission). Left: the home preview, chip monitoring and the icon's local token (still the development Mac's).

**Milestone 5, in progress (2026-11-03)**: mouse and keyboard. Mac-only Kyber patch `server/macos/kyber-patches/0002` (injection through `CGEvent`, see [kyber-changes.en.md](kyber-changes.en.md)); Accessibility permission granted by the author to "KyberNow Station (Kyber)". **Mouse and keyboard checked from the PC** (2026-11-03). Pitfall found during the test: a Mac plugged twice into the same network (Ethernet and Wi-Fi) answered over UDP from its main route's address; the PC, which aimed at the Wi-Fi address (kept since pairing), rejected those answers and never got the picture. Cause: quinn-udp, Kyber's QUIC library, asks for the source address through `IPV6_PKTINFO` (dual-stack socket) or `IP_RECVDSTADDR`, which macOS ignores when sending; only `IP_PKTINFO` is honoured (test of 2026-11-03). Patch `server/macos/crates/quinn-udp-0.5.14-source-mac.patch`: Kyber answers from the address that was called, whichever it is. On top of that, Admin only announces the main route's address (Ethernet before Wi-Fi, as the author wants), reread every 15 s. **Checked from the PC with Wi-Fi on** (2026-11-03: session through the Wi-Fi address, picture, mouse and keyboard). But the whole session then stayed on Wi-Fi: `prepare` now gives `kyber_host`, the Ethernet address, to a device of the same network, and the apps' core takes the picture there (Admin is still reached at the kept address); to be tried with a Windows app built from this branch. Pointer: shape and position announced to the apps by kynput (Mac patch `0003`, see [kyber-changes.en.md](kyber-changes.en.md)), read from the real pointer on a thread (56 × 80 pixels at Retina scale); **checked from the PC** (2026-11-03: pointer visible, in place, shapes followed); hidden pointer (game, typing) followed through `CGCursorIsVisible`, tried with an app hiding it through `NSCursor.hide`, `CGDisplayHideCursor` then `setHiddenUntilMouseMoves` (typing); with the desktop mouse, the device's app keeps its pointer, as with a PC: the hidden pointer drives Auto mode, with the full screen Admin now sees on Mac (`foreground.rs`, front window covering a display, except browsers and players). Clipboard: text and HTML both ways, with the service's rights (Mac patch `0004`); round trip on the real pasteboard checked from a thread; **checked from the PC** (2026-11-03, copy and paste both ways). System keys: the PC's ⊞ key is ⌘ on the Mac; ⊞+Tab stayed on Windows (Task View): the Windows app now grabs any key held with ⊞ (to try with the next version's app); ⌃⌘Q and ⇧⌘Q refused to guests and borrowers (Mac patch `0005`, author's choice); the apps' "Keys" menu facing a Mac (⌘⇥, ⌘ Space…) comes with milestone 8, with the "Ctrl acts as ⌘" option. **Locked Mac checked from the PC** (2026-11-03): session opened on an already locked Mac (⌃⌘Q), picture of the lock screen, password typed from the PC that unlocks it (`loginwindow` log: locked 17:29:09, session 17:29:20, unlocked 17:29:40); locked during a session, the picture stays. Nothing to add: Kyber runs in the user's session, which locking does not close. Out of scope, as chosen: the login window after logging out or a restart (no session left, so no Kyber). Milestone 5 is done, except the apps' "Keys" menu and "Ctrl acts as ⌘" option (milestone 8).

**Milestone 3, in progress (2026-11-03)**: virtual display. Admin starts the `kybernow-display` agent (Swift, `server/macos/display-agent`, driven by `display/mac.rs`): `CGVirtualDisplay` displays at the device's resolution and refresh rate, Retina from 2048 pixels wide (a readable interface on a phone, tablet, Mac or 4K TV; 1080p at 1x), up to 4 displays placed like the device's. During the session, **the Mac's displays are switched off**, as on Windows (author's choice, 2026-11-03, after a first version where they mirrored the virtual display): the main virtual display becomes the main display (at (0, 0), the Mac's displays placed against its right), then the Mac's displays are switched off **one per configuration** (`CGSConfigureDisplayEnabled`), waiting for each; several at once, macOS switched them off late, one at a time and out of order, and the author's Asus XG32UQ, deprived of signal, only came back when unplugged. One at a time: off in 1.8 s, back on with the previous layout in 2.6 s (Asus, Studio Display and LG TV). Safety net: switched-off displays are written to `~/Library/Application Support/KyberNow/display-off.json` and switched back on by the next agent, by `kybernow-display recover` when Admin starts, and by the agent if Admin stops; agent killed during the test: everything came back (12 s). **Pitfall** (first session, 2026-11-03): Admin removes the virtual displays before `restore`; for a moment with no display at all, macOS turned on the MacBook's built-in screen (lid closed) and no longer switched the others back on: the agent therefore switches the Mac's displays back on when its last virtual display is removed, before removing it (checked in that order). **Checked in a session from the PC** (2026-11-03): the three displays off during the session, back on at the end in the same layout, Asus included. Lending the computer: displays kept on. Switching them off (`CGSConfigureDisplayEnabled`, private) was applied by macOS only several seconds late, sometimes only when the program exited. Safety net: the virtual display lives with the agent, which lives with Admin, and changes are made "for this program only"; if either stops, macOS gives the Mac's displays back in place (checked, including a session without heartbeat, closed after 20 s). Mac-only Kyber patch (`server/macos/kyber-patches/0001`, see [kyber-changes.en.md](kyber-changes.en.md)): txproto follows displays that appear and disappear, and announces them in pixels. Checked on the M4 Max: `prepare` at 2868 × 1320 at 120 Hz in 1.8 to 2.3 s, Kyber announces only the virtual display (2868 × 1320 at (0, 0)) and captures it, mode change during the session, end of session. Pitfalls: a Retina display is declared in points (macOS makes the Retina mode out of it; declared in pixels, it takes twice that and its "half" mode is not usable for the desktop); when the virtual display appears, macOS also changes the mode of the Mac's main display, restored afterwards. **Session from the iPhone at its resolution checked by the author** (2026-11-03: virtual display ready in 1.6 s, 2868 × 1320 at 120 Hz, picture on the first try, HEVC at 56 Mbit/s, the Mac's displays back at the end). Left: multiple displays from a Mac with several screens, HDR of virtual displays (offered later). **Multiple displays from the PC** (the author's test, 2026-11-04, two 4K displays): only one display out of two. **Pitfall**: a process does not see the mode of a display that appeared after its first request to macOS (`CGDisplayCopyDisplayMode` and `CGDisplayCopyAllDisplayModes` stay empty there; running the event loop or subscribing to changes makes no difference, another process sees it), while its bounds follow: the agent waited 3 s for the 2nd display's mode when creating it, then `isolate` returned it as absent and Admin removed it. The agent now relies on the bounds and the mode it asked for (`shown`), waits for every display to be in place before working out scales and positions, and places a display left of the main one at its own scale (`toPoints`). Checked by driving the agent (two 4K, a 4K and a 1440p Retina, displays side by side), then **tried successfully from the PC** (2026-11-04: two 4K displays, at 160 and 60 Hz, the second at (−3840, 0), ready in 1.5 s instead of 9 s).

**Milestone 4, in progress (2026-11-03)**: sound. Core Audio driver `server/macos/audio-driver` (`KyberNow.driver`, C, AudioServerPlugIn): a "KyberNow" device, an output of 2, 6 or 8 channels at 48 kHz (WAV order: `WAVE_5_1_B`, `WAVE_7_1` layouts) that plays nothing on the Mac, and a loopback input that gives back what is played there (read then cleared: nothing played, silence); never the default microphone. Installed by hand (`sudo cp -R … /Library/Audio/Plug-Ins/HAL/`, `sudo killall coreaudiod`) until the package (milestone 6). Admin (`audio/mod.rs`, `mac::MacBackend`) sets it to the device's channel count and makes it the default and alert output for the session, through the agent (`kybernow-display audio route|restore|status`, `display-agent/audio.swift`); switch and return checked (Studio Display → KyberNow 5.1 → Studio Display). Driver clock measured: 512 frames every 10.67 ms, no jump. **Pitfall**: captured by ScreenCaptureKit, the sound played on KyberNow reached the device stuttering (smooth on the Mac's speakers); Kyber therefore reads the loopback input through Core Audio (Mac patch `0006`), which also gives 5.1 and 7.1; it needs the Microphone permission for "KyberNow Station (Kyber)" (`NSMicrophoneUsageDescription` set by `run-kyber.sh`). For the notarised package (hardened runtime), the `com.apple.security.device.audio-input` entitlement will be needed. **Checked from the PC** (2026-11-03): smooth stereo sound through the loopback input ("KyberNow audio capture started"), the Mac's speakers silent, original output restored at the end. Not tried yet: 5.1 and 7.1 (they need a device asking for them, the LG TV and its amplifier for instance).

**Milestone 7, in progress (2026-11-03)**: advanced features. Lending the computer will come with milestone 6 (author's choice): its "console mode" is carried by the tray icon on Windows, it will be the menu bar icon on Mac. Share and relay: nothing Windows-specific in Admin (`share.rs`, `share_api.rs`, `relay.rs`); for the browser guest, kycontroller serves the web client engine from a `webclient` folder (`webclient` setting of `kyber_config.toml`): the test Station builds it like the Windows overlay, the official Kyber 0.29 folder then our engine (`kyber-web-out`, which does not depend on the system), through `run-station.sh`. **Pitfall** (test of 2026-11-03): the iPhone guest joined then went back to the home screen, Kyber showing it an empty display list: Admin numbered the shared display as on Windows (CRC-32 of the name), whereas the ScreenCaptureKit capture numbers its displays through `sp_iosys_gen_identifier` (CRC-32 of the context type, the macOS display number and the entry type); `kyber_display_id("mac:<number>")` now does that same calculation (checked on the author's two displays). The guest then stayed on "First images": its own image (scaled down, 1080p at 60 Hz) was refused, VideoToolbox not being counted among the encoders that can scale it; Mac patches `0007` (scaling through `scale_vt`) and `0008` (rate capped by ScreenCaptureKit). **Share checked with the iPhone** (2026-11-03): the guest joins, gets its own 1080p image, and keyboard and mouse given by the host from the PC. Not tried yet: the browser guest, the relay (`share.kybernow.app` refused the connection that day). App at session start: `launch.rs` (`mac` module) goes through the agent (`kybernow-display apps|launch|close|locked`, `display-agent/apps.swift`): catalogue of the Applications folders (the Mac's, Utilities, system, user's) with their icons (141 apps on the author's Mac), Steam Big Picture offered if Steam is there (`steam://open/bigpicture`, closed by `steam://close/bigpicture`), opened through `NSWorkspace` (app brought to the front if it was open), closed by `terminate`, waits for unlock; "Other…" browser on Applications, the user's apps and the Desktop. **Checked in a session** (2026-11-03: App Store opened for the PC at session start); not tried yet: closing at the end, Steam Big Picture. HDR: a `CGVirtualDisplay` display becomes HDR through its mode's transfer function (`CGVirtualDisplayMode … transferFunction: 1`, private property found on 2026-11-03; values 0, 2, 3 and 4: SDR): macOS then sees it as HDR (`SLSDisplayIsHDRModeEnabled`, EDR up to 5×); the agent switches a virtual display to HDR or SDR at the same mode (`set_hdr`, 0.6 s, `display/mac.rs`), Admin offers HDR on Mac, and Kyber captures 10-bit PQ and encodes HEVC Main 10 (Mac patches `0009` and `0010`). **Pitfall** (test from the iPhone, 2026-11-03): a dull HDR image. ScreenCaptureKit puts the desktop's white at 100 nits in its PQ image (measured: 10-bit level 509), where the Windows Station puts it at the device's SDR white (203 nits by default); the Mac's virtual display has no known luminance field (its description only carries primaries, white point and identifiers). The capture therefore raises the image on the GPU (Metal): P010 PQ → R'G'B' → linear × (device white / 100) → PQ → P010 (test outside a session: white 100 → 201 nits, black unchanged, hues kept); Admin writes the wanted white, per display, to `~/Library/Application Support/KyberNow/hdr-sdr-white.json` when switching the display to HDR. Kyber's log gives the white applied ("Capture: hdr option 1 … SDR white 203 nits") and, every 240 frames, the brightest level ("HDR: brightest level"). **Checked from the iPhone** (2026-11-03): HDR10 session, white applied at 203 nits (brightest level 220 to 227 nits), image judged good by the author. An iPhone screenshot during an HDR session comes out flipped (the live image is not): an iOS quirk with HDR content, not KyberNow's.

**Milestone 6, in progress (2026-11-03)**: app, installer, icon. Everything fits in one app, `/Applications/KyberNow Station.app`: the menu bar icon is its main executable (Swift, `server/macos/menubar`), next to Kyber (kycontroller, kyavserver, kynputserver and their libraries), Admin, the display agent and `kybernow-ui` (the windows); the `KyberNow.driver` sound output and the web client engine are in its resources. **A single "KyberNow Station" line in macOS settings**: macOS ties permissions to the bundle that contains the executable (test of 2026-11-03: an executable of the Kyber bundle, started as its own responsible process, saw the bundle's permissions; started plainly by another program, it saw that program's); Admin gains screen recording (home preview). Everything runs in the user's session, as LaunchAgents in `~/Library/LaunchAgents` (Kyber, Admin, the icon), like the test Station: no LaunchDaemon, since the virtual display, sound and apps only live in an open session. Data in `~/Library/Application Support/KyberNow/Station` (`kybernow.json`, `kyber/`, `admin/`), logs in `~/Library/Logs/KyberNow`. The `.dmg` (`server/macos/scripts/build-station-app.sh`, Developer ID signed, hardened runtime with the `com.apple.security.device.audio-input` entitlement) carries "Install KyberNow Station" and "Uninstall KyberNow Station"; windows follow the mockup validated by the author (Claude Design canvas), same Svelte interface and Rust core as the Windows installer (`server/installer/ui/src/mac`, `server/installer/src/mac`); details in [server/installer/README.en.md](../server/installer/README.en.md#station-for-mac). The Mac's password is asked once, through macOS's window (AppleScript with administrator privileges): app copy, sound output, firewall (if on) and wake on network. The Permissions step starts the installed app's executable while disclaiming responsibility (`responsibility_spawnattrs_setdisclaim`) to read and request the three permissions, and checks each line by itself. **Pitfalls** (first installation, 2026-11-03): macOS's `openssl` (LibreSSL) writes the key's curve in full instead of its name, then a version 1 certificate: rustls, in Kyber, refused one then the other and Kyber restarted in a loop; the key now comes from `ecparam` (named curve) put into PKCS#8, the certificate carries v3 extensions, and the installation checks that Kyber answers on its port. Admin said "No compatible graphics card": the Apple chip is now its card (`gpu.rs`, VideoToolbox). Sharing showed a 4K display in "larger text" mode at macOS's working size (6016 × 3384): the agent gives the panel's resolution (native mode). Image and sound said "Simulated: Admin isn't running on Windows": the state now follows the real engine (virtual display, KyberNow sound output), simulation being left for development only; Admin's tests no longer look at the Station installed on the Mac that runs them. Admin's Windows-specific texts (Start menu, SudoVDA driver, wake, lending, logs, events; about thirty) have their Mac version, used on a Mac Station (rule in [i18n.en.md](i18n.en.md#texts-specific-to-the-stations-system)), and Admin's "Restart the Station" works on Mac (launchd restarts Kyber then Admin). **Installation checked on the M4 Max** (2026-11-03: checks, account, Mac password, three permissions checked, Kyber, Admin and the icon running). Updating from the icon or Admin: a `KyberNow-Station-Mac-update.zip` package (the whole app) published with each release and listed by the signed manifest, Admin's Mac applier (`update/mac.rs`, details in [releases.en.md](releases.en.md)), the icon's window through Admin's local routes. **Notarized** (2026-11-03, `build-station-app.sh --notarize`): the app then the .dmg accepted by Apple, tickets stapled, Gatekeeper accepts the app, "Install" and "Uninstall" ("Notarized Developer ID"). Lending the computer: same console agent as on Windows (`kybernow-console`, Mac part in `system_mac.rs` and `steam_mac.rs`), Admin's Mac part (`lend_sys.rs`), icon; details in [pret.en.md](pret.en.md#mac-station). **Lending tested successfully** (2026-11-03, from the iPhone, code accepted from Admin: virtual display, launcher, covers, Steam, end and lock) after three fixes: the icon's notification and buttons, the agent's windows without native full screen, and Kyber patch 0012 (the capture removed the Station's windows from the image, hence the launcher). **Session from a device on the installed Station tested** (2026-11-03, Windows app and iPhone): the sound went out 6 % too slow (slowed, cuts, growing delay), fixed by Kyber patch 0013 (10 ms frames); afterwards sound at the right speed, no cuts, a delay of a few milliseconds that doesn't grow. **Scales of a 4K display** (2026-11-04, the author's request): from 3840 pixels wide, the virtual display has every macOS scale, like a real 4K display (System Settings › Displays, from "1280 × 720" to "3840 × 2160"); it presents itself as a 27-inch, and macOS recommends "2560 × 1440" there (drawn at 5120 × 2880); the scale chosen in Settings is remembered for that definition (one serial number per definition); the image sent stays at the device's definition (Kyber patches 0014 and 0015). Phones and tablets keep the Retina mode alone (macOS's recommendation would give them a smaller interface). **Tested in a session from the PC** (2026-11-04, 3840 × 2160 at 160 Hz): macOS shows "2560 × 1440" (drawn at 5120 × 2880), Kyber sends 3840 × 2160, sharp text, mouse and keyboard used throughout the session.

## Choices

| Topic | Choice |
|---|---|
| Supported Macs | Apple silicon only (M1 and later), macOS 15 Sequoia or later. No Intel Macs |
| Engine | Kyber 0.29's macOS server (kycontroller, kyavserver with txproto, kynputserver), with our patches. No engine of our own |
| Admin | The same `kyber-admin`, built for macOS, same routes and same interface; Windows-only parts get their Mac equivalent behind the same modules |
| Virtual display | `CGVirtualDisplay`, Apple's private API (the one BetterDisplay and DeskPad use): the device's resolution and refresh rate, up to 4 displays; during the session, the Mac's displays are switched off, as on Windows (author's choice of 2026-11-03, going back on the mirroring chosen first). No App Store, and a macOS release can break it: checked at every beta |
| Sound | A KyberNow virtual audio device from the first version (Core Audio plug-in, 2 to 8 channels), like the virtual speakers on Windows |
| Gamepads | Not in the first version: keyboard and mouse. Virtual gamepads through CoreHID, ready (03/11/2026), waiting for Apple's `com.apple.developer.hid.virtual.device` entitlement; as on Windows, DualSense for a PlayStation gamepad, Xbox Series Wireless for any other (see [Gamepads](#gamepads)) |
| Locked Mac | The unlock screen is streamed and the password can be typed. After a restart (FileVault), the session must be opened in front of the Mac or automatic login set |
| First version | Everything the Windows Station does, except gamepads: virtual display and multiple displays, sound, profiles, pairing, wake, Share and relay, Lend the PC, HDR, app at session start, updates from Admin |
| Tests | On the author's Mac (M4 Max) as the Station, to the Apple TV, the iPhone, the PC and the LG TV |

## What already exists

- **Kyber can serve from a Mac** (0.29, "Add macOS server support"): ScreenCaptureKit capture of picture and sound (`txproto/src/iosys_screencapturekit.m`), VideoToolbox encoding (H.264, HEVC), keyboard and mouse injected by `kynput/src/macos/host_keyboard_mouse.rs`, `tech.kyber.server` LaunchAgent in the user's session and at the login window. The libavconv engine has no Mac capture: txproto only.
- **Admin already runs on a Mac** for development, with simulated drivers (virtual display, sound, wake, app catalogue, local token, preview through `screencapture`, system name through `sw_vers`). Windows-only modules sit behind `cfg(windows)`: the simulations get replaced with the real thing.
- **The icon** (`server/tray`) is made of crates that exist on Mac (tao, tray-icon, wry); only its system calls are Windows-specific.
- **The apps already read what the Station can do** in `GET /api/stream/info` (`virtual_display.max_screens`, `speakers`, `hdr`, `wake`, `os`). A Mac Station describes itself there, and the apps adapt without knowing it is a Mac.

## macOS permissions

- **Screen Recording** and **Accessibility**: granted once, at install, through the welcome window that explains why.
- **macOS 15 monthly reminder** for apps that record the screen: to request from Apple, the `com.apple.developer.persistent-content-capture` entitlement (meant for remote desktop) avoids it. Without it, the Station must say so plainly in Admin and in the icon.
- **Login window**: capture and typing there go through a process started at the login window (`LimitLoadToSessionType` `LoginWindow`, like Kyber's LaunchAgent): check this first, it is the least certain part.

## What the KyberNow Link apps see

As few changes as possible, and only through what the Station announces:

- `GET /api/stream/info` already gives `os` ("macOS 26.1"); it gains `gamepads`: `{ "available": false, "reason": "entitlement" }` until Apple grants its entitlement (`helper` without the helper), `available: true` on Windows and on an entitled Mac ([Gamepads](#gamepads)). Living-room apps then say "Gamepads unavailable on this computer" instead of showing the gamepad row, and every app says so with a brief notice during the session (milestone 8, [link-ui.en.md](link-ui.en.md), “Controllers unavailable”).
- **Keyboard**: a PC, phone or TV connecting to a Mac sends Ctrl where the Mac expects ⌘. A "Ctrl acts as ⌘" option, offered only with a Mac Station, with its default in the core.
- **Wake**: the help text talks about the Mac's setting instead of the network adapter and BIOS.
- Rules and texts are written first in [link-ui.en.md](link-ui.en.md), then carried into every app.

## Gamepads

**Status (03/11/2026)**: gamepads **work** on the M4 Max's installed Station with Apple's development entitlement (evening test from the iPhone, see below); a published version needs the distribution entitlement, requested from Apple the same day. Without any entitlement, macOS refuses to create a virtual gamepad: CoreHID's `HIDVirtualDevice` returns `nil`, and an executable signed with the entitlement but no profile allowing it is killed at launch.

**The path.** CoreHID (`HIDVirtualDevice`, macOS 15) is the only one that works under Developer ID. Apple's support (developer forums, DTS answers) confirms it: this entitlement is enough, no need for DriverKit (heavier, with its own entitlements to request; according to Apple, `com.apple.developer.driverkit.family.hid.virtual.device` does nothing). Karabiner-VirtualHIDDevice only does keyboard and mouse, for root only; kernel extensions are out.

**What games will see.** The macOS extension that recognises gamepads (`AppleGameControllerPersonality.kext`) explicitly accepts, even when virtual (`GCIOMatchVirtual`), the DualSense (054C:0CE6), DualSense Edge, DualShock 4 and the Xbox wireless controllers over Bluetooth, including the Xbox Series (045E:0B13); not the Xbox 360 nor wired Xbox controllers. So the Station creates, as on Windows: a **DualSense** for a PlayStation gamepad on the device, an **Xbox Series Wireless Controller** for any other one (or for all of them with Admin's "All gamepads as Xbox" setting). Reports are the real gamepads' (descriptors captured from real ones), which GameController (Mac games), SDL and Steam read. No touchpad, motion sensors or adaptive triggers: Kyber's protocol does not carry them (same on Windows). Rumble goes back to the device.

**What is ready.**

- Mac Kyber patch `0011` (`kynput/src/macos/host_gamepad.rs`, [kyber-changes.en.md](kyber-changes.en.md)): device gamepads plugged, DualSense and Xbox reports, rumble sent back.
- The **KyberNow Manettes** helper (`server/macos/gamepads`, Swift): background app in `KyberNow Station.app/Contents/Helpers`, started by kynputserver on the first gamepad plug, driven through a pipe; it creates the gamepads through CoreHID, answers the DualSense's feature reports and sends output reports (rumble) back. End of session: the gamepads go away with it. It has its own App ID, `fr.leslignesclaires.kybernow.station.gamepads`, to carry the entitlement's Developer ID profile (Apple's pattern for an executable with a restricted entitlement) without touching the main app.
- `server/macos/gamepads/build.sh` (called by `build-station-app.sh`) sets the entitlement and the profile as soon as a valid Developer ID profile is there (`KYBERNOW_GAMEPADS_PROFILE`, otherwise Xcode's profile folders); without a profile, the helper is signed without the entitlement.
- Admin: `gamepads` in `GET /api/stream/info` is `{ "available": false, "reason": "entitlement" }` until Apple answers (`kybernow-gamepads --check`, once per Admin launch), `reason: "helper"` without the helper, `{ "available": true }` on Windows and on an entitled Mac. Kyber's log, in session: "macOS refused virtual gamepad … lacks Apple's com.apple.developer.hid.virtual.device entitlement".
- Tried on the Mac: report and rumble tests (kynput's `cargo test`), the whole chain Kyber → helper → macOS (refusal reported), Admin.
