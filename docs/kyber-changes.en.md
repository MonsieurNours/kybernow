# What KyberNow changes in Kyber

English · [Français](kyber-changes.md)

KyberNow is built on Kyber 0.29 (AGPL-3.0, sources in `third_party/kyber-desktop`). Kyber's code is never modified in place in this repository: each change is a patch stored here, applied by a script at build time. Everything else (virtual display, virtual audio output, cursor, accounts) goes through KyberNow Admin and Kyber's configuration, without touching its code.

| Patch | Where | What it changes | Why |
|---|---|---|---|
| `server/kyber-patches/0001-kyavservice-son-hd.patch` | kyavservice (server) | Opus bitrate according to the number of channels, configurable: `[kyavserver] audio_quality` = `standard` (128 kbit/s, Kyber's fixed value), `hd` (default: 256 kbit/s in stereo, 96 kbit/s per channel beyond that), `studio` (510 kbit/s in stereo, 256 kbit/s per channel); `audio_bitrate` in bit/s takes precedence. The txproto engine keeps the layout of the captured output (stereo, 5.1, 7.1). Two limits of Kyber, older than the patch: txproto and libopusenc refuse any layout outside the Vorbis order (5.1 *side*, quad, 6.1…) — the encoder does not open and there is no sound —, and Kyber's web client plays sound in hard-coded stereo (`kywebplayer/src/audio/mod.rs:29`), so it stays silent when the computer outputs 5.1 or 7.1 (with libavconv, `audio_layout = "stereo"` avoids it, see 0008). | 128 kbit/s for everything, even in 7.1: poor sound. |
| `server/kyber-patches/0002-txproto-curseur-stable.patch` | txproto `dxgi_cursor.c` (server) | A pointer hide is only sent after 250 ms without the pointer coming back; an unusable shape is ignored without changing the position or the visibility. | Windows hides the pointer for a few frames at the slightest keystroke or shape change: on the client, the pointer flickered and switched to relative mouse. |
| `server/kyber-patches/0003-txproto-son-continu.patch` | txproto `iosys_wasapi.c` (server) | Sound timestamps follow the samples, realigned on the WASAPI capture clock (QPC) if they drift from it by more than 40 ms or at each discontinuity. Packets marked silent are filled with zeros. | Packets read in bursts shared almost the same timestamp (“Queue input is backward in time”): choppy, distorted sound. Windows does not define the content of a silent packet. |
| `server/kyber-patches/0004-txproto-son-basse-latence.patch` | kyavservice `txproto/audio.rs` (server) | Opus packets of 10 ms instead of 20, Opus in `lowdelay` mode (CELT only, without SILK's look-ahead). WASAPI capture does not change: it follows the period of the Windows audio engine (10 ms by default); the duration given to the capture (`buffer_ms`) is only read by PulseAudio. | Encoder delay down from 26.5 ms to 12.5 ms: 10 ms less frame and 4 ms less SILK look-ahead. At the bitrates of 0001, the quality does not change to the ear. |
| `server/kyber-patches/0006-txproto-pointeur-deplacements.patch` | txproto `dxgi_cursor.c`, `iosys_dxgi.c`; kyavservice `config.rs`, `txproto/` (server) | Pointer moves are forwarded too (position only, empty bitmap) while it is visible, at most `[kyavserver] cursor_move_rate` times per second: 60 by default, 120 at most, 0 to forward only shape and visibility changes as Kyber does. kyavservice passes the rate to the DXGI capture through the `cursor_move_rate` option. The input server forwards these positions without a shape (0011). | Kyber only sends the position when the pointer appears, disappears or changes shape. In game mode (relative mouse), the Mac's pointer is hidden and the image does not contain Windows' pointer: in a game's menus, no pointer would be seen. With these positions, the app draws it in the right place. |
| `server/kyber-patches/0005-kycontroller-image-cle.patch` | kycontroller (server) | New route `POST /force_idr`: forces a keyframe (IDR) on the video streams of the session that requests it, through the same mechanism Kyber uses when one of its relays falls behind. Same authentication and same scope as `/set_bitrate`. At most one keyframe per session every 150 ms: a closer request is ignored (still answered 200, the keyframe is on its way) and logged at `debug` level. | With the encoder's progressive refresh (Kyber's default setting), NVENC never sends a keyframe by itself. When packets are lost beyond what error correction can repair, VLC carries on with a damaged image that repairs itself little by little; VideoToolbox, however, refuses all following frames and the image stays frozen. So the client requests a keyframe. Without a limit, a client that keeps losing packets would get a keyframe per round trip, and every client of a shared stream would pay for it. |
| `server/kyber-patches/0007-kynet-envoi-image.patch` | kynet `driver/common.rs` (server) | Three `CommonServerOptions` options: size of the QUIC datagram send queue, of their receive queue, and of the UDP socket send and receive buffers. Without a value, nothing changes (quinn's 1 MB queues, system buffers). KyberNow's values come from 0010. | Video goes out as datagrams, and quinn drops the oldest ones once its send queue is full. A large 4K frame or a keyframe fills the 1 MB queue while pacing spreads it out: pieces of frames are lost on the computer itself, then the keyframe requested again fills it once more. On the Mac side, nothing is lost (client patch 0003). |
| `server/kyber-patches/0008-kyavservice-moteur-libavconv.patch` | kyavservice `avconv/` and libavconv-rs (server) | The new engine on a par with the historical one. **Displays**: the list is read again without a forced graphics card, and IDs are the CRC-32 of the Windows name (`\\.\DISPLAY2`), as with txproto. Capture picks the display by that ID. **Pointer**: moves forwarded (position only, at most `cursor_move_rate` per second as in 0006, counted from the last packet actually sent to the input server), hide announced after 250 ms; a pointer that shows again is sent with its shape. When the input server connects, it gets the current state with the pointer's shape; a hide still pending stays pending. **Sound**: 5.1 and 7.1 kept (Opus channel mapping family 1, channels named in the Vorbis order libopus requires, side mapped to back by aresample), stereo otherwise; `[kyavserver] audio_layout = "stereo"` goes back to Kyber's stereo mix for every client (`native` by default; no effect on txproto); 10 ms `lowdelay` packets. The frame size (480 samples) is announced to clients, read from the encoder's parameters. | With a forced card, Kyber's engine only re-reads the outputs known when it started: the virtual display never appears, switched-off displays stay at 0 × 0, and the numbers 0, 1… differ from one engine to the other. The pointer only moves on shape changes (frozen in the web client) and blinks. Sound is stereo, in 20 ms packets. Before FFmpeg 8, FFmpeg's "5.1" name means 5.1 *side*, which libopus refuses. Kyber announces a zero frame size: a Kyber client with unreliable sound (`Unreliable`, `UnreliableFec`) stops on an assertion when it receives it. Pitfall: dating a move by its planned sending time, rather than by the last packet actually sent, freezes the pointer above 60 Hz as long as the mouse moves (every frame pushes the sending back). |
| `server/kyber-patches/0009-libavgrab-son-continu.patch` | libavgrab `wasapi.c`, `avgrab.c` (server) | Sound timestamped from the sample count, resynchronised on the WASAPI capture clock (QPC) beyond 40 ms of drift or on each discontinuity; silent packets filled with zeros; channel count of each audio output (`AVGrabSource.nb_channels`); option to keep the provider's timestamp. | As 0003 for txproto: arrival time gives the same timestamp to packets read in one go (sound "going backward" for the encoder and the player). |
| `server/kyber-patches/0010-kycontroller-file-d-envoi.patch` | kycontroller `config.rs`, `kymux_controller/mod.rs` (server) | Configurable send policy: `[kycontroller] datagram_send_queue = "deep"` (default: deep 8 MB queue per connection) or `"short"` (short 3 MB queue, about three of the largest 4K frames); `datagram_send_queue_size` (in bytes, at least 64 KiB) replaces the size of the chosen policy. Receive queue and UDP buffers always at 8 MB. The controller logs the policy at startup ("Datagram send queue: Short, 3145728 bytes per connection"). Admin: System › Advanced › Image send queue. | Under congestion (saturated Wi-Fi), an 8 MB queue holds 0.7 to 2.2 s of already stale frames before dropping them. The short queue bounds that delay: the oldest frames are dropped, the client asks for a keyframe again. Which one to choose depends on measurement (see below). |
| `server/kyber-patches/0011-kynput-pointeur-positions.patch` | kynput `windows/host_cursor.rs`, kynputservice `pipeline_state.rs` (input server) | A position received without a shape goes to clients without a shape (`CursorData::None`) as long as the shape they have is this display's. The last shape is only put back when needed: pointer showing again, other display, transparent shape (which kynput's filter turns into a hidden pointer). The state kept for clients connecting later keeps the shape, at the last position. | Without it, the input server puts the full bitmap back into every position packet: 240 KiB/s to 1 MiB/s on each client's reliable stream, one PNG conversion per move for the web client, and the official client recreates its cursor 60 times per second. This caps the rate at 60 per second. Clients keep the last shape they got: the KyberNow Link app (the core's `PointerLayer` only replaces the shape when the packet carries one) and Kyber's web client (`client_cursor.rs` ignores a visible pointer without a PNG) keep drawing; Kyber's official client does not change its cursor, but does not reapply the shape after a click release or when coming back into its window (`windows_statemachine.rs` keeps the last packet, without a shape): a minor defect, which keeps this part out of the series offered upstream (see below). |
| `server/kyber-patches/0012-kynput-compilation-croisee.patch` | kynputserver `build.rs` | The small macOS-only C program is only compiled when the *target* is macOS. | The original build script tests the machine doing the build: built from a Mac for Windows, kynputserver tries to assemble the macOS code with MinGW and fails. |
| `server/kyber-patches/0013-kynput-client-web.patch` | kynput `wasm/client_keyboard.rs`, `wasm/client_gamepad.rs`, `Cargo.toml` (web engine) | **Text**: what is typed into a field marked `data-kynput-text` goes out as `Unicode` packets (type 10), read on `beforeinput` (text, paste, Enter, Backspace, Delete) and `compositionend` (input methods, dictation, accents), the field being emptied afterwards; a `beforeinput` the page already handled (`preventDefault`) is left alone. Keys of a composition (`isComposing`, code 229) do not go out as keys. **Release everything**: on `blur`, hidden tab and lost Pointer Lock, the server releases keys, buttons and gamepads (`FlushKeys`, as `flush_keys()` does), and gamepads then send their actual state again. **Gamepads**: those whose `mapping` is not `standard` are ignored (the table only applies to it); the `requestAnimationFrame` loop stops with the engine. | Kyber's engine reads the keyboard by `code` only: wrong on an AZERTY computer from a phone, nothing for accents or composition; the page has to force WebSocket to slip the text in itself. A key or a stick stays held when the tab goes to the background. A gamepad with an unknown layout sends random buttons, and the gamepad loop keeps running after the engine stops (reference cycle). |
| `server/kyber-patches/0014-kywebplayer-decodeur.patch` | kywebplayer `video/decoder.rs`, `video/player.rs` (web engine) | `flush()` before a new `configure()`; delta frames dropped until the next keyframe (after a configuration or an incident) instead of an `assert!`; a WebCodecs error (decoder closed by the browser) recreates the decoder with the last configuration, and the error is only reported (so the session ended by kyclient) if no keyframe comes within a second. Reception dates counted for decoded frames only. | In Kyber's engine, a delta packet right after a configuration change makes it panic, and the slightest decoding error ends the session. Limit: with NVENC's progressive refresh, the computer does not send a keyframe by itself, so after a real decoding error the session still ends up cut (after a second); the web engine cannot request `/force_idr`. |
| `server/kyber-patches/0015-kyberweb-position-absolue.patch` | kyber-web `src/pointer_lock.rs` (web engine, `kyber/apps/kyber-web` repository) | Relative moves only when the pointer is actually locked; otherwise (lock pending, refused by the page, impossible on a touch screen), absolute positions keep going out, even when the computer hides its cursor. When the lock is lost (Escape), back to positions. | As soon as Windows hides its cursor (typing, no mouse plugged in), Kyber's engine stops sending positions and waits for a lock that the page refuses in desktop mode or that does not exist on a touch screen: a tap or a click goes to the wrong place, and the page has to send the position itself (WebSocket only). |
| `apps/macos/kyber-patches/0002-kynput-presse-papiers.patch` | libkynput (client) | C functions for the clipboard: `kynput_clipboard_text_{change,request,unavailable,data}_to_packet`, `kynput_clipboard_event_from_packet`, `kynput_clipboard_text_from_packet` (text, 60 KB at most, UTF-8 cut cleanly). | Kyber only has a clipboard handler for Windows, Linux and the web, and its C API can neither read nor build these packets. The apps make the link with NSPasteboard (Mac) and UIPasteboard (iPhone, iPad). |
| `apps/macos/kyber-patches/0001-kyclient-paquets-audio-video.patch` | libkyclient (client) | `kyclient_video_player_config_set_packet_sink` and `kyclient_audio_session_config_set_packet_sink`: packets (`kyclient_MediaPacket`: type, codec, config, keyframe, pts, lost samples, data) go to a callback in the app instead of VLC. Without a callback, nothing changes. New module `media_sink.rs`, forwarding task in `kymux_backend/desktop.rs`. Also `kyclient_client_request_keyframe`: `POST /force_idr` to the controller (server with 0005), with no effect on a server that does not know it (refusal logged); the request runs in a task of its own, one at a time, given up after one second, so that it never delays the loop's other messages (stop, reconnection). Last call `KYCLIENT_MEDIA_PACKET_KIND_CLOSED` when the forwarding task ends, whatever the reason (stop, failure, cancellation): the app then knows it may release whatever `userdata` points to. Watch out: `kyclient_video_session_config_default` copies the player's configuration, so the video callback must be set before it (otherwise the image goes to VLC). The KyberNow core (`apps/core/src/media.rs`) uses it through the Rust crate (`kyclient::media_sink`). | The app decodes by itself (VideoToolbox + Metal, Opus + Core Audio): decoding in 1 to 3 ms, most recent frame always shown, variable refresh rate displays followed, sound with about twenty milliseconds of buffer instead of a fixed 50 ms, without depending on VLC (on iOS and tvOS too). |
| `apps/macos/kyber-patches/0003-kynet-tampon-de-reception.patch` | kynet `driver/quinn.rs` (client) | The QUIC client's UDP socket is created by KyberNow (socket2) with an 8 MB receive buffer (6, 4 or 2 MB if the system refuses), instead of macOS's 768 KB default. QUIC's queue of received datagrams also goes to 8 MB. | A 4K frame arrives as one burst, faster than the socket is read: with the default buffer, it overflows and the Mac drops bursts of 20 to 30 packets in games ("dropped due to full socket buffers"), so keyframes had to be requested again. |
| `apps/webos/kyber-patches/0001-kynput-client-webos.patch` | kynput `Cargo.toml`, `lib.rs`, `capi/mod.rs`, `error.rs` (webOS and Linux clients) | With `--cfg kybernow_webos`, kynput behaves as on Android: client configuration only, without Linux input injection (libinput, libevdev, X11), and Linux key codes converted to Windows scancodes. | The LG TV is a Linux without those libraries: kynput's server part does not build there, and the client does not need it. The Linux app (desktop, Raspberry Pi) uses it too: client only, without the server's input injection or its libraries. |

## Applying and rebuilding

- **Server**: `server/kyber-patches/build.sh` puts the files concerned back in their original state (git), applies all the patches in order (`*-kycontroller-*` and `*-kywebplayer-*` in `kysdk/kyctl`, `*-kynet-*` in `kysdk/kymux`, `*-kynput-*` in `kysdk/kynput`, `*-kyberweb-*` in `third_party/kyber-web`, the others in `kysdk/kymedia`, txproto and libavconv subprojects included), rebuilds kyavserver and txproto for Windows from macOS (MinGW, UCRT), then kycontroller (Rust, same options as the official release: `auth-jwt,auth-oidc,cli,kyhub,win32-hide-console,win32-tray`), then the input server (`kynput.dll`, linked against Kyber 0.29's `SDL2.dll`, and `kynputserver.exe`), then the web client's engine (`kyclient_wasm.js` and `kyclient_wasm_bg.wasm`, in the overlay's `webclient/`; built from an original copy of `kysdk/kyctl` plus only the `*-kywebplayer-*` patches, since `third_party`'s `kysdk/kyctl` also carries the apps' patches). Finally it assembles `third_party/payload/kyber-overlay/`, with next to it a fingerprint of the patches and the script (`kyber-overlay.stamp`) that `scripts/release.sh` checks. The installer carries Kyber 0.29's files with this overlay laid on top; an update (Admin's applicator or `update.ps1`) copies `kyber\` with the new overlay and keeps the previous version in `kyber.prev`. Details of the cross-compilation: [build-notes.en.md](build-notes.en.md).
- **macOS client**: `apps/macos/scripts/build-kyclient.sh` applies each patch to the repository named by its file (`*-kyclient-*`: `kysdk/kyctl`, `*-kynput-*`: `kysdk/kynput`, `*-kynet-*`: `kysdk/kymux`), rebuilds libkynput and libkyclient (`cargo cinstall`) and replaces them in `apps/macos/Vendor/`.
- **Client core** (`apps/core`, Apple and Windows apps): the `kyclient` crate is built from `kysdk/kyctl`; `apps/core/scripts/build-apple.sh` and `apps/windows/scripts/build.sh` also apply the client patches (`apps/macos/kyber-patches`) before building.
- **Apple TV client**: `apps/tvos/scripts/build-kyber-tvos.sh` applies the same patches, builds libkynput (without SDL: gamepads go through GameController), libkyclient and libopus as static libraries for Apple TV and its simulator (Rust nightly, `-Zbuild-std`), adds empty functions for the libvlc calls (never reached: image and sound go to the app) and puts everything into `apps/tvos/Vendor/KyberSDK.xcframework`.
- **Android client**: `apps/android/scripts/build-native.sh` applies the patches in `apps/macos/kyber-patches`, builds libkynput (without SDL) and libopus for each ABI, then the app's native library (`libkybernow.so`).
- **Linux client** (desktop and Raspberry Pi): `apps/linux/scripts/build.sh` applies the patches in `apps/macos/kyber-patches` and the one in `apps/webos/kyber-patches` (kynput as a client only, `--cfg kybernow_webos`), then builds libkynput, FFmpeg reduced to decoding, and the app.
- **LG TV client**: `apps/webos/scripts/build.sh` applies the patches in `apps/macos/kyber-patches` then the one in `apps/webos/kyber-patches`, builds libkynput (without SDL) and libopus for webOS's armv7 target, then the app. The SDL-webOS patches (`apps/webos/sdl-patches`, gamepad detection) do not touch Kyber.

These scripts stop at the first error (patch that does not apply, failed build) without replacing anything, and report a toolchain different from the checked one: see [build-notes.en.md](build-notes.en.md#build-scripts-real-failure).

Adding a patch: change the sources in `third_party/kyber-desktop`, then save the difference here. For the server, a `NNNN-sujet.patch` file in `diff -u` format (paths `a/…` and `b/…` relative to the target repository: `kysdk/kymedia`, `kysdk/kyctl` for `*-kycontroller-*`, `kysdk/kymux` for `*-kynet-*`, `kysdk/kynput` for `*-kynput-*`, `kysdk/kyctl` for `*-kywebplayer-*`, `third_party/kyber-web` for `*-kyberweb-*`), made against the original plus the earlier patches, since several of them touch the same files. For the client, `git -C kysdk/kyctl diff -- kyclient` or `git -C kysdk/kynput diff -- kynput`, in a file named after the repository (`NNNN-kyclient-…`, `NNNN-kynput-…`, `NNNN-kynet-…`). Then complete the table above, in both languages.

## Measuring the send policy (0010)

The setting exists to decide by measurement between the deep queue (nothing lost on the computer, possible delay under congestion) and the short queue (image on time, possible hiccups).

1. Choose the policy in Admin (System › Advanced › Image send queue) or in `kyber_config.toml`:
   ```toml
   [kycontroller]
   datagram_send_queue = "short"      # or "deep" (default)
   # datagram_send_queue_size = 2097152   # another size, in bytes
   ```
2. Restart Kyber (Admin offers to). The controller log must show `Datagram send queue: Short, 3145728 bytes per connection`.
3. Saturate the Wi-Fi during a session (for example a continuous download on another device on the same access point, or `iperf3 -c <server> -R -t 120` from the Mac), then note the latency (the app's HUD), lost frames and keyframe requests (`/force_idr` in the controller log at `debug`).
4. Repeat the same measurement with the other policy, and without saturation to check that neither degrades the normal case (4K, keyframe).

## To check on the computer (patches 0006 to 0015)

The patches build from the original sources (full `build.sh`, 21/10/2026). Still to check on the computer:

- **Send policy**: the measurement above, on a saturated Wi-Fi, deep queue against short queue (and an intermediate size with `datagram_send_queue_size`). The default only changes afterwards.
- **Pointer**: with `[kyavserver] cursor_move_rate = 120`, the pointer the app draws in game mode follows the mouse smoothly, with txproto and with libavconv; the shape stays right after a shape change, a hide, a move from one display to another; a device connecting during a session gets the shape. kynputserver's log without errors; much lower throughput on the inputs connection while the mouse moves.
- **Replaced input server**: `kynputserver.exe` starts with Kyber (ViGEm gamepads, keyboard, clipboard as with Kyber's); the computer's official client `kyclient.exe` starts with the overlay's `kynput.dll` (SDL gamepad included).
- **Web engine** (the `/ecran` web client's session is checked end to end, touch and phone and tablet keyboards included): tab hidden then shown again, Alt+Tab, Escape in Game mode: nothing stays held; pointer hidden by Windows in Desktop mode: clicks land in the right place over WebTransport; non-"standard" gamepad ignored; display mode change during a session (new decoder configuration) without a crash.

## Handled without changing Kyber's code

- **Configuration** (`kyber_config.toml`, through Admin): port, encoder, single Basic account, JWT secret drawn at random at installation (instead of the development key shipped with Kyber, in `C:\ProgramData\KyberNow\kyber-jwt.key`), Admin settings (Picture and sound, System › Advanced), comments kept and a backup at each write (the last 30).
- **Virtual display**: SudoVDA (Apollo 0.4.6's driver), created by Admin for each session at the size of the client's display. If Windows does not activate it by itself, Admin helps it once a second (extended desktop, then a supplied layout with that single display); after 8 s, the failure says what was seen. The layout is saved by Windows (`SDC_SAVE_TO_DATABASE`, `CDS_UPDATEREGISTRY`) so that it does not reapply it in a loop. Removed at the end of the session, original displays restored.
- **Sound**: default output switched to Steam's virtual speakers (Steam Streaming Speakers) with the right number of channels during the session, then put back as before. Sound therefore does not come out of the computer's speakers.
- **Pointer**: “Hide pointer while typing” turned off for the duration of the session, then turned back on.
- **Capture engine**: KyberNow works with both engines of Kyber 0.29, the historical one (`[kyavserver] backend = "txproto"`, the default) and the new one (`libavconv`). Each fix is ported to both: 0002, 0003, 0004 and 0006 for txproto, 0008 and 0009 for libavconv; 0001 (Opus bitrate), 0005, 0007, 0010 and 0011 apply to both.
