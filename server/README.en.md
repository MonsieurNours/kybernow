# KyberNow Station (Windows)

English · [Français](README.md)

KyberNow Station, everything that runs on the Windows computer that streams the picture: the Kyber 0.29 server (patched, see [docs/kyber-changes.en.md](../docs/kyber-changes.en.md)), KyberNow Admin (the Station's administration in the browser), the notification area icon and the installer that sets it all up.

| Folder | Contents |
|---|---|
| `admin/` | KyberNow Admin, `kyber-admin.exe`: Windows service (Rust, axum), HTTPS |
| `web/` | Admin's interface (Svelte) and the KyberNow Link web client (`/link`), embedded in the binary |
| `tray/` | KyberNow Station's notification area icon, `kybernow-tray.exe` |
| `installer/` | `KyberNow-Station-Setup.exe`, see [installer/README.en.md](installer/README.en.md) |
| `kyber-patches/` | Server-side patches to Kyber and their build script |

## KyberNow Admin (`kyber-admin`)

Installed by `KyberNow-Station-Setup.exe`, as a Windows service, on a port drawn at random at installation (shown at the end, and in the notification area icon). The account is the one chosen during installation.

v2 identity (Archivo, Martian Mono, Spectre signal, “console” symbol), five pages by intent, menu on the left and tabs at the bottom on a phone. Choices apply immediately; Kyber's need a restart, offered at the top of the page. Addresses from previous versions (`#/dashboard`, `#/logs`…), which may still be bookmarked, lead to the page that holds them.

| Page | Role |
|---|---|
| Overview (`#/ensemble`) | The screen preview in large; during a session, the connected device, since when, its profile, its latency and “End the session”; the state in four cards (server, virtual display with the number of displays and their modes for a session with several displays, sound, update), the latest devices and today's feed |
| Picture and sound (`#/image-son`) | SudoVDA virtual display (trigger, default mode, if a game changes the resolution, 15 s test, turn the displays back on), sound (trigger, channels, Opus quality), keyboard, mouse and gamepads (clipboard, Xbox 360, repeat) |
| Link devices (`#/appareils`) | Add a device (QR code and `kybernow://` link, certificate fingerprint), access requests with a code (Apple TV: accept, refuse), one card per known device that opens on its settings (app at session start and its options, access, sessions, “End the session”, forget or remove access), and the switch that lets Kyber serve several devices at the same time (Kyber's `network.multi_client` setting) |
| Users (`#/utilisateurs`) | Kyber accounts (Basic): one person per username and the devices that use it, password change, deletion, addition; the own access of a device accepted with a code is read-only there |
| System (`#/systeme`) | One-click updates, server (start, stop, graphics card, ports) and “Restart the Station” (the server and Admin, see below), “Wake on LAN” (whether Windows lets the Ethernet, or Wi-Fi, card wake the computer, and what to do if not; see below), logs by source (connections, picture and sound, commands, Admin, other; filter, follow, download, level of detail), Advanced: Kyber's raw settings (NVENC, AMF, Quick Sync or x264 encoder, chosen at installation according to the graphics card; engine, progressive refresh, minimum bitrate, port, addresses, image send queue, connection methods), `kyber_config.toml` editor, Admin password |

**Devices and event feed** (`activity.rs`). KyberNow Link apps introduce themselves in `POST /api/stream/prepare` (`device`: stable identifier, name, type, system, app version; `profile`), give their median latency with their heartbeat (`latency_ms`) and that of the whole session at the end. Admin keeps the last 50 devices (`devices.json`) and the last 300 events (`events.json`): connections, disconnections with duration and latency, interrupted sessions (no heartbeat for 20 s: `activity::HEARTBEAT_GRACE`, the same delay for the session, the app's virtual display and the full-screen watch), accounts, restarts, updates. An app older than 0.2.1 counts as “one device” per account. The session is identified by the device (`device_id`, sent by apps from 0.2.5 on with their heartbeat and their session end; by the account for an older app): two devices on the same account are not confused. **One device at a time.** If a second device prepares while a first one is in session, Admin asks the first to end (it learns it at its next heartbeat, `end`, and disconnects cleanly) and makes the second wait up to 7 s; if the first no longer answers, its session is closed and the display taken over. The virtual display is then recreated at the second device's mode. A replaced device that disconnects afterwards does not touch the display or the sound of the one that took over. Admin routes: `GET /api/devices`, `DELETE /api/devices/{id}`, `GET /api/events?limit=`, `POST /api/session/end`, `GET /api/preview?width=` (screen preview, as for the apps). `GET /api/status` also gives the current and the last session (`activity`) and the available update.

**App at session start** (`launch.rs`). For each device, Admin can open an app on the computer as soon as its virtual display is ready: Steam Big Picture for the Apple TV, Playnite, a spreadsheet for a remote desktop… Set under Link devices (the device's card, “At session start”: the app, then its two switches), kept on the device (`Device.launch` in `devices.json`: `kind` = `app` (Start menu entry, by its Windows application identifier), `uri` (a suggestion's address, `steam://open/bigpicture`) or `path` (executable or shortcut); `target`, `name`, `icon`, `exe`, `close`, `close_at_end`, `skip_desktop`). **No path to type**: the picker offers the detected suggestions (Steam Big Picture, Playnite Fullscreen, Xbox, GOG Galaxy, Epic Games, EA app, Ubisoft Connect, Battle.net, when installed), the user's whole Start menu with its icons (`shell:AppsFolder`: classic and Store apps, pinned games), and an “Other…” browser limited to Program Files, Program Files (x86), the Desktop and the user's apps (`.exe`, `.lnk`). The Start menu and Store apps belong to the signed-in account: the `display-agent apps` agent reads them **with the user's account** (`agent::run_as_user`: console session token, result and icons written in their profile, `AppData\Local\KyberNow`), Admin copies the catalogue and the PNG icons into `apps/` in its data folder; without a Windows session open, the previous catalogue stays, with the error. Routes: `GET /api/apps` (catalogue, read the first time), `POST /api/apps/refresh`, `GET /api/apps/icon/{name}`, `GET /api/apps/browse?path=` (refused outside the allowed folders), `PUT /api/devices/{id}/launch` (`{"launch": {…}}` or `null`; an address must be a suggestion's, a path must exist in an allowed folder). **Flow**: in `prepare`, once the virtual display is in place, `display-agent launch` runs with the user's account (`ShellExecuteEx` of the address, of `shell:AppsFolder\…` or of the executable); an app opened by Admin for another setting (another device) is closed first; an app already open (known executable) is brought to the front; with the Windows session locked, Admin waits for the unlock for up to 2 min (`launch::UNLOCK_WAIT`); in the Desktop profile, nothing opens when “Not in the Desktop profile” is checked. The `prepare` response gives `launch` (the app's name). At the end of the session (`end`, lost heartbeat, takeover), the app is closed when “Close the app at the end of the session” is checked: by its closing address (`steam://close/bigpicture`), otherwise `WM_CLOSE` to the windows of the launched process or of the executable; a device taking over with the same app keeps it open (`expect_takeover`, 60 s). A watch every 2 s closes the app of a device no longer in session. The event feed records openings, closings, waits for unlock and failures. Outside Windows (development Mac), a simulated catalogue and launches that only go to the log.

**Languages** (`i18n.rs`, `server/web/src/lib/i18n/`, shared rules in [docs/i18n.en.md](../docs/i18n.en.md)). Admin and the web client exist in French and English: the browser’s language (`navigator.languages`, French if the first one starts with `fr`, English otherwise), or an “Auto”, “Français”, “English” choice (System › Advanced, under the left menu, on the sign-in screen and in the web client’s settings), kept in the browser (`localStorage`, `kybernow.lang`, shared by Admin and the web client). Texts live in `src/lib/i18n/fr.json` (the source) and `en.json`, same keys; `t('screen.key', { name })`, `tn()` for plurals; a key missing in English falls back to French, and `npm run check` verifies that both files have the same keys and the same parameters, and that every key used exists. Every API call sends `Accept-Language` with the chosen language, and **Admin answers in the request’s language**: error and refusal messages (including those returned to the apps, such as “the server will restart as soon as the session of … ends”), update status (`verify_error`, `install_error`, `error`), release notes, event feed sentences, Kyber settings texts (`GET /api/schema`). Language from `Accept-Language`: the preferred language (weight, then order), French if it starts with `fr`, English otherwise; **no header means French** (apps from before the two languages). On the Rust side, embedded `src/i18n/fr.json` and `en.json` catalogues, `tr(lang, "key", &[("name", …)])`; Kyber settings keep their French in `schema.rs` and their English in `src/i18n/schema.en.json` (a test checks nothing is missing). A text produced outside a request and read later (event, refused version, failed installation) is kept as a key and parameters (`i18n::Msg`) and written when read. Release notes: the GitHub release carries the French, a `<!-- en -->` line, then the English; Admin only returns the part for the requested language (the whole text without the marker, for versions before 0.3.0). Logs (`kyber-admin.log`) stay in French.

**Event feed format** (`events.json`). Each event keeps `at`, `kind` (`info` or `warn`), its key and parameters (`key`, `params`: `{"key": "events.connected", "params": {"name": "Apple TV"}}`) and its French sentence (`text`, read as is by an Admin older than 0.3.0 after a rollback). A parameter can be a text, a number, another message (`{"key", "params"}`), a list (`{"list": [...]}`), a duration (`{"duration": seconds}`), a latency (`{"ms": 8.3}`), a Kyber setting (`{"field": "video.encoder"}`, written as its label) or a text already written in each language (`{"fr", "en"}`, for an error). `GET /api/events` rewrites `text` in the request’s language; an event recorded by a version older than 0.3.0 only has `text` and is shown as it is.

**Graphics cards** (`gpu.rs`), for NVIDIA, AMD and Intel. A dedicated thread reads Windows' cards again every 5 minutes (`Win32_VideoController`, same sorting as the installer: working NVIDIA, AMD and Intel PCI cards, with the manufacturer's driver, in that order; the first one is the one that encodes) and reads Windows' “GPU Engine” counters every second (`\GPU Engine(*)\Utilization Percentage`, WDDM 2.x, the Task Manager's), tied to each card by its LUID (DXGI). From them it gets the load of each card, of its encoder and of its decoder (busiest engine; “Video Codec”, the shared engine of some AMD and Intel cards, counts for both), and knows whether a stream is running: `kyavserver.exe` uses a card's encode engine (the stream stays “running” 15 s after the last encoded frame, since a still screen may give nothing to encode), or NVML counts an NVENC session. This signal is used by the screen preview (no capture during a stream) and by the safety nets of the virtual display and the sound (“for any connection” trigger, an app session with no news). For NVIDIA cards, NVML adds NVENC sessions, frames per second, encoding latency, performance state, temperature, power and memory. In `GET /api/status`, `gpu.devices` gives for each card `name`, `vendor` (`nvidia`, `amd`, `intel`), `driver` (NVIDIA number, 560.94, or Windows' one), `encoding`, `gpu_utilization`, `encoder_utilization`, `decoder_utilization` and, for NVIDIA, NVML's fields; `gpu` is `null` without a compatible card. Without “GPU Engine” counters (Windows too old), only NVML reports activity.

**Ending a session.** A KyberNow Link app learns it at its next heartbeat (`"end": true`, 5 s at most) and disconnects cleanly; another client (browser, command line) is cut by restarting Kyber. `POST /api/local/end` does the same from the icon, reserved for the computer itself (see “Local routes”).

**The virtual display during the session** (`display/mod.rs`, `display/watch.rs`). While a session holds the virtual display, an agent launched in the Windows session (`display-agent watch`, like the full-screen watch) reads every second the current mode of the virtual display (`EnumDisplaySettingsW`, `ENUM_CURRENT_SETTINGS`, on the display's GDI name found from its adapter and target) and the active displays (`QueryDisplayConfig`), and writes them to `display-watch\state.json`; it stops by itself after 15 s without news from Admin or when `display-watch\run` carries another session's token (never two agents), and Admin relaunches it if it stays silent for more than 10 s. The current mode and the number of active displays are given to the apps with the heartbeat and in `GET /api/display` (`mode`, `displays`). A mode different from the one obtained at creation (within 1 Hz: a game switching to 1080p, a Windows setting) is announced once in the event feed, then the **mode policy** decides: `follow` (“Let it be”, default) keeps it, `restore` (“Put it back”) puts the session's mode back (`ChangeDisplaySettingsExW` through the agent, `display-agent set-mode`), at most once every 5 s; against a game that imposes its resolution again after each change, it gives up after three changes in a minute and lets it be for the rest of the session (announced, `mode_policy` is then `follow`), unless “Put back” is used again. The `virtual_display.on_mode_change` setting (Picture and sound, “If a game changes the resolution”) applies to clients that say nothing; the apps send `mode_policy` according to their profile (Game: `follow`, Desktop: `restore`, the others: `default`, the setting), in `prepare` and with each heartbeat (profile changed during the session). In `restore`, a new call to `prepare` at the same mode also puts the mode back right away (the apps' “Put back” button). A physical display that turns back on during the session (cable plugged back in, Windows reapplying a layout) is turned off again after 2 s of stability, by reapplying the virtual display's isolation (at the current mode in `follow`, at the session's mode in `restore`; at most once every 10 s), and the feed says so. If Windows keeps turning it back on (five isolations in two minutes) or the isolation fails three times (first attempt after 2 s of stability, then 20 and 40 s later; one message at the first failure), Admin gives up for the rest of the session and announces it once. Outside Windows, the simulated driver sees the requested mode.

**Several displays** (`display/mod.rs`, `display/topology.rs`, shared contract in [docs/multi-ecrans.en.md](../docs/multi-ecrans.en.md)). An app that wants all of the device's displays sends `screens` in `prepare`: from 1 to 4 displays `{width, height, refresh, x, y, primary}`, in pixels on the Windows desktop. Admin checks them before touching anything (a single `primary`, at (0, 0); each mode within limits; no overlap; all linked to the main one by shared edges, a corner is not enough), otherwise `400` and `{"error": …}`. Then one SudoVDA display per entry, the main one first: it keeps the usual identifier (`KyberNow-Display`, name “KyberNow”, serial `KYBERNOW-0001`), the next ones get their own (`02-KyberNow-Disp` to `04-…`, “KyberNow 2” to “KyberNow 4”, `KYBERNOW-0002` to `-0004`; SudoVDA makes the first 4 bytes of the identifier the EDID serial number, different for each display so that Windows does not mix them up), so that Windows finds each one's scale again from one session to the next. The driver heartbeat starts as soon as the first display is created. The agent (`display-agent isolate-many --screen luid_low,luid_high,target,width,height,refresh,x,y`, once per display) waits for Windows to activate them (8 s, helping it as for one display), keeps only those active (physical displays off), saves the layout in the Windows database, applies modes and positions at once (`ChangeDisplaySettingsExW` with `CDS_NORESET`, the main one with `CDS_SET_PRIMARY`), saves the final layout again, then reads back each one's mode and position. A display that Windows leaves at another mode stays against its neighbour, on the requested side (a display left of the main one keeps its right edge, a display above it its bottom edge). As the agent has no log, what it notes while placing the displays (mode or position refused with the Windows code, requested mode offered by Windows or not) goes to Admin's log (“écrans virtuels : …”). A display that the driver refuses or that Windows does not activate is removed and is `null` in the answer, with a warning in the feed; the main one is required (otherwise the preparation fails as today, all displays removed). The answer gives `screens` in the order of the request, mode and position read back; `applied` stays the main display's mode. The session file (`display-session.json`, `guids` field) lists every display for `recover`; the end of the session removes them all. The watch (`display-agent watch --extra luid_low,luid_high,target`, once per secondary display) reads each one's mode: a changed mode is announced display by display, `restore` puts each one back (one fix counted per round, whichever displays are affected), and a physical display turned back on is turned off by putting each display back at its mode and position from the start of the session. Without `screens`, without a virtual display (`trigger` Off, `virtual_display: false`) or in “For every connection”, nothing changes: one display, as before. The feed says how many displays the session took (“Mac Studio connected, 3 displays: 3840 × 2160 at 160 Hz, …”); the Overview shows their number and modes, `GET /api/display` gives them in `session.screens` (current mode and position, the main one first) with `session.screens_requested`.

**Pairing link.** `GET /api/pairing` (Admin session) gives the `kybernow://` link that Link devices shows as a link and a QR code (address, Admin's port, its certificate's fingerprint; no secret).

**Pairing with a code (Apple TV)** (`pairing.rs`). Without typing anything on the remote: the Apple TV draws a 6-digit code, shows it and sends it to every Station found over Bonjour, without an account: `POST /api/pair/request` (`{"code", "device": {id, name, kind, os, app}}` → `{"id", "expires_in"}`). The request appears under Link devices with the device's name and its code in large type (Accept, Refuse), in a banner on the other spaces with a badge on Link devices, and in the icon's panel, which opens by itself for a new request, without the code (it is compared in Admin, which accepts) and lets you refuse (`POST /api/local/pair/{id}/refuse`, reserved for the computer itself; `accept` exists too, the icon does not use it). Only accept if the code is the one shown on the TV. The device polls `GET /api/pair/request/{id}`, without an account: `pending`, `refused`, `expired` (also for an unknown request), or `accepted` with `username` and `password`, delivered once only (the request disappears at once). Accepting (`POST /api/pair/accept/{id}`, Admin session) creates **a Kyber account of its own** for the device: identifier drawn from its name (“Apple-TV-du-salon-3f9a”), random 128-bit password. Both Admin and Kyber accept it (Basic, like an account typed by hand); the app saves it as for a normal addition, with nothing changed on the client side. Kyber only reads its accounts at startup (`kycontroller/src/auth/basic.rs`): Admin restarts it at once (in the background) if nobody is connected. Otherwise the access is kept **pending** (`access.rs`, in memory) and Kyber restarts by itself as soon as it serves nobody: no app session left (session ended or 20 s without heartbeat), no virtual display or sound in use, no encoding (15 s after the last frame), no session being prepared; Admin checks every 5 s (`api::supervise_access`) and writes it in the feed (“Server restarted to give access to …, now that nobody is connected”). If the device connects before that, `prepare` restarts Kyber before answering, provided no other device is in session (up to 20 s for the encoding of a session that just ended to drop, then 12 s for Kyber's port to reopen); otherwise `409`, with a message the app shows (“the server will restart as soon as …'s session ends”): the other device is neither cut off nor taken over. Admin banner (“Server restart pending to give access to …”, with “Restart now”) and the icon's panel show it; `GET /api/status` and `GET /api/local/state` give these accesses (`pending_access`: `account`, `device`, `grant`), apart from changed settings (`restart_pending`, still applied by hand). Any restart of Kyber by Admin covers pending accesses; those of a stopped Kyber are read when it starts. The device enters the list before its first session (“Paired just now”, “own access”); “Remove access” (`DELETE /api/devices/{id}`) deletes its account, asks its session to end if it has one, and Kyber follows at the restart, awaited as above (Admin refuses it right away). Under Users, these accounts are labelled “Device access” and point to the device's card, with no password change. A device paired again loses its previous account. Limits (requests without an account): exactly 6 digits, 10 requests per minute and 2 pending per address, 6 pending in all, a new request from the same device replaces the previous one; 5 min to accept, then 2 min to collect the access (otherwise the created account is deleted). Requests only live in memory. `GET /api/status` gives the pending requests with their code (`pair_requests`); `GET /api/local/state` gives them without the code (`id`, `name`, `kind`, `expires_at`) and counts them (`pair_requests_count`).
Why not a JWT of the device's own, signed by Admin with Kyber's key? Kyber cannot revoke a single one (the key would have to change, cutting every token), and the app would have to go through `kyclient_auth_credentials_new_jwt` and renew it. The own account can be revoked one by one and changes nothing in the apps.

**For the apps.** Admin announces itself over Bonjour (`_kybernow._tcp`, TXT `v`, `name`, `fp`, `kyber`), hence the UDP 5353 firewall rule. `kyber=1`: a Kyber server is behind it (its configuration is there and its Windows service exists); `kyber=0`: Admin without a Kyber server (development Mac, incomplete installation), no session would ever start there and the apps don't offer this Station. An announcement without `kyber` (Admin from an earlier version) is still offered. It also serves the session API:
- `GET /api/stream/info`: name, system (`os`, for example “Windows 11 Pro 24H2”, absent if unknown), GPU, AV1, virtual display (with `max_screens`, the number of displays the Station can create for a session: 4; absent before multiple displays), speakers, and `station` for the “Station” section of the apps' settings, read from memory without any network call: the Station's version (`version`), its update (`update`: `available` and `version` for a newer release signed by KyberNow, `installable` from a device, `requires_setup` when the installer is needed, `installing`) and `restarting` (a restart has been accepted: Admin is about to stop); a Station 0.4.9 or older has no `station`. And `wake`, the network cards used to wake the computer (see “Wake on LAN” below), also read from memory; a Station 0.4.9 or older has no `wake`. And `account.own_device`: true when the calling account was created for a device by code pairing (the apps show it as “This device's own access”). `GET /api/status` (Admin) also gives `os` and `wake`. On Windows, the name comes from the registry (ProductName and DisplayVersion, “Windows 11” from the build number, as ProductName still says “Windows 10”); on the development Mac, from `sw_vers`; on Linux, from `PRETTY_NAME` in `/etc/os-release`;
- `GET /api/stream/preview?width=960`: preview of the main display as it is right now, for the background of the apps' home screen. JPEG (quality 70), width bounded between 320 and 1600 (960 by default), height to ratio, `X-Captured-At` header (RFC 3339). `503` and `{"error": "…"}` if the screen cannot be captured: nobody signed in, screen locked or a security prompt shown, agent unavailable. The last capture is served again for 10 s (5 s for a failure); during a session (KyberNow Link app or another Kyber client: kyavserver encodes, on an NVIDIA, AMD or Intel card), no capture is taken: the last one is served again, or `503`. The capture is taken by an agent launched in the Windows session (`display-agent preview`, GDI, main display scaled down to the requested width), which writes the JPEG to `preview\`; on the development Mac, by `screencapture` (screen recording permission needed);
- `POST /api/stream/prepare`: virtual display at the client's size (or one per display of the device, optional `screens` field: see “Several displays”), sound with the right number of channels; the app introduces itself there (`device`, `profile`) and says what to do if the mode changes during the session (`mode_policy`: `follow` or `restore`, optional). If another device is in session, the answer waits until it has handed over (7 s at most, see above); for an accepted account Kyber has not read yet, it restarts Kyber first (32 s at most) or answers `409` if another device is in session (see “Pairing with a code”): allow a 40 s timeout for this call. The session is only counted once the display is in place; the answer also gives `kyber_fingerprint`, the fingerprint of Kyber's certificate (`sha256:…`, the one the relay pins), which the apps require when connecting instead of keeping the first certificate (reinstalling the Station changes it), and `launch`, the name of the app opened at the start of the session (`null` without a setting, see “App at session start”);
- `POST /api/stream/heartbeat`: heartbeat (without it, the virtual display disappears), with the current latency and `device_id`; the answer says whether Admin asks for the session to end (`end`: from Admin, or because another device is taking over) and whether the virtual display in place is this device's own (`active`), with the current mode of the virtual display (`mode`: `width`, `height`, `refresh`, which may have changed during the session) and the number of active displays on the computer (`displays`), `null` until the watch has read them, and the policy in force (`mode_policy`); the app may send `mode_policy` there (profile changed during the session). A new call to `prepare` by the device already in session (display requested again after Kyber restarts) continues the same session: no new connection in the event feed and no extra session for the device;
- `GET /api/stream/foreground`: app in the foreground on the computer, full screen or not, game or not (Auto mode of the apps' mouse). Admin gets it from an agent that runs in the Windows session for the duration of a session (`display-agent foreground`, state written every 400 ms). The agent stops by itself after 20 s without a heartbeat;
- `POST /api/stream/end`: original displays and audio output given back, with a report; the app gives the session's median latency and `device_id` there. If the display has meanwhile gone to another device, nothing is given back (`kept_for`);
- `POST /api/stream/station/restart`: restarts the whole Station (see “Restarting the Station” below); optional body `{"device_id": "…", "force": false}`, `202 {"ok": true}` before stopping;
- `POST /api/stream/station/update`: the same installation as `POST /api/update/install`, same body; the package is downloaded and verified before the answer (allow a few minutes), then `202 {"ok": true, "version": "…"}`. `409` with no version installable from a device (`code`: `up_to_date`, `requires_setup` when the installer is needed, `not_installable` with the reason), during an installation (`installing`) or a restart (`restarting`), or if a device is in session without `force` (`session`, with `device`, its name). Admin's activity feed notes “{device} started the update to {version}”;
- `POST /api/pair/request`, `GET /api/pair/request/{id}`: pairing with a code, without an account (see above).

**Updates** (Admin account): `GET /api/update` (installed version, `channel`, latest release of the channel, prerelease or not, notes; `installable` only if the signed manifest is verified and compatible, otherwise the reason in `verify_error` and `requires_setup` when `KyberNow-Station-Setup.exe` is needed), `PUT /api/update` (`{"channel": "stable" | "beta"}`, saved in `update_channel`, returns the state after a new check), `POST /api/update/check`, `POST /api/update/install`, `POST /api/update/rollback` (back to the version in the `.prev` folders, given in `rollback` of `GET /api/update`, `null` when there is none). Those last two answer 409 if a device is in session, unless the body is `{"force": true}`. Signing and channels: [docs/releases.en.md](../docs/releases.en.md#update-signing-key-minisign). If the applicator stops without having replaced Admin, or the update fails, `GET /api/update` returns `install_error` (with the end of the log) and the installation can be started again. `GET /api/local/state` (reserved for the computer itself, for the icon) also gives `update_available`, `version`, the computer's name, its address and the current session (`activity`).

**Wake on LAN** (`wake.rs`). So that the KyberNow Link apps can turn on a computer that is off or asleep without anything to type, `GET /api/stream/info` gives `wake`: the physical network cards in use, Ethernet first, then Wi-Fi, the card with the default gateway first, each with `mac` (`AA:BB:CC:DD:EE:FF`), `ipv4`, `broadcast` (the subnet's broadcast address, computed from the prefix), `kind` (`ethernet` or `wifi`), `armed` (Windows lets the card wake the computer, from `powercfg /devicequery wake_armed`; `null` if `powercfg` does not answer) and `name` (the card, as in Device Manager). The apps keep this list for each computer and send the magic packet through the core (`apps/core`, `wake` module). The cards come from `GetIfTable2` (what the card is: physical connector as with `Get-NetAdapter -Physical`, medium, filter interface) and `GetAdaptersAddresses` (IPv4 addresses and prefix, gateway); virtual cards (Hyper-V, WSL, VPN, virtual machines, also recognised by their name), Bluetooth, the loopback and the addresses Windows gives itself when there is no network (169.254.x.x) are left out. A card bound to a Hyper-V virtual switch has no address of its own: it takes the one of the virtual card that carries the same MAC address. A dedicated thread reads the cards again every minute and `powercfg` every 5 minutes, and the log notes each change; `info` and `status` only read memory. Admin's System page shows a “Wake on LAN” line from it: “Allowed”, “Not allowed” or “Unknown” for the first card, and otherwise what to do (allow wake on magic packet in the network card's properties, and in the BIOS), with a warning for Wi-Fi (waking only works there with some cards, from sleep); “Unavailable” without an Ethernet or Wi-Fi card in use. Outside Windows (development), a simulated Ethernet card, at the computer's address, with a locally administered MAC address (`02:4B:4E:00:00:01`) that no card carries.

**Restarting the Station** (`station.rs`). “Restart the Station” (Admin's System page, `POST /api/station/restart` with Admin's session; the “Station” section of the apps, `POST /api/stream/station/restart`) restarts the Kyber server **and** Admin, like the icon's menu. Admin cannot stop in the middle of its own answer: it starts a detached assistant, `kyber-admin restart-station` (hidden command, as SYSTEM, outside the service's “job” like the update applicator), and answers `202`. The assistant waits 2 s for the answer to leave, stops Admin then Kyber (30 s each; a service stuck while stopping has its process stopped), then starts Kyber and Admin again, even if a stop failed: the `kyber-admin` service has no automatic restart. Log of the last restart: `C:\ProgramData\KyberNow\station\redemarrage.log` (the assistant's output: `lancement.log`). Refusals: `409` during an installation (`code`: `installing`), a restart already accepted (`restarting`, two minutes at most) or a session (`session`, with `device`, the device's name), unless `{"force": true}`; `429` less than a minute after the previous one (`too_soon`, with `retry_after` and the `Retry-After` header; the time is kept in `station\dernier-redemarrage`, which survives Admin's restart). An installation or a rollback is refused (`409`) during a restart: the assistant runs from the `admin` folder they rename. Admin's activity feed notes “{device} restarted the Station” (the name comes from `device_id` if the known device uses that account, otherwise “A device on account …”), or “Station restarted from Admin”. Admin's sessions do not survive the restart: the System page waits for `GET /api/session` to answer again, then the sign-in screen comes back. The button of the “Settings changed” banner only restarts Kyber (`POST /api/service/restart`), to apply its settings. Outside Windows, the restart answers `500` (`failed`).

**Admin fingerprint for the icon** (`tls.rs`, `publish_fingerprint`). `init` and every start write the SHA-256 fingerprint of Admin's certificate to `C:\Program Files\KyberNow\kybernow.json` (`console_fingerprint`), next to `kyber\`, if the file exists and it changed: the icon only accepts that certificate (see [server/installer/README.en.md](installer/README.en.md#notification-area-icon-servertray)).

**Local routes** (`local_token.rs`). `GET /api/local/state`, `POST /api/local/end` and `POST /api/local/pair/{id}/accept|refuse` serve the person in front of the screen, through the icon. They require the loopback address (also `::ffff:127.0.0.1`) **and** a token: Admin draws 32 random bytes at its start and at every Windows logon (the service receives `SERVICE_CONTROL_SESSIONCHANGE`, `WTS_SESSION_LOGON` and `WTS_CONSOLE_CONNECT`, and renews 2 s later), writes them in hexadecimal (64 characters) to `C:\ProgramData\KyberNow\local-token` (reserved to SYSTEM and Administrators), then runs `kyber-admin display-agent local-token --dir …` in the user's session; the agent copies the token into the profile of the account signed in to that session (`%LOCALAPPDATA%\KyberNow\local-token`, permissions inherited from the profile: that account and administrators), a copy retried six times 5 s apart if the session is not ready. The icon reads that file at every call and sends it in the `x-kyber-local` header; constant-time comparison, `403` without a token or with one from a previous start. Another account on the computer, or a sandboxed process without access to the profile, can therefore neither end the session nor answer a pairing request. Off Windows, the token is only written to `dev-data/local-token`.

Authentication is Basic, with the Kyber account. The apps pin Admin's certificate by its fingerprint. Every request other than `GET` to `/api/*` must carry the `x-kyber-admin` header (its value is not read), otherwise `403`: a third-party site cannot add it without a CORS preflight, which Admin does not allow. The apps, the icon and Admin's interface send it. The two Station routes accept any Kyber account (any paired device, by code or by password: the right depends only on the account, never on the declared `device_id`) and Admin's session. They share the Admin sign-in lockout, per address: a refused account counts there as a wrong password (answer slowed down by 0.8 s) and, after five, they answer `429` (`code`: `locked`, `retry_after`); a success does not clear these failures, so that a Kyber account cannot be used to clear those of the Admin sign-in. The other `/api/stream/*` routes are not locked. Their refusals carry `error` (in the request's language) and `code` (`session`, `installing`, `restarting`, `up_to_date`, `requires_setup`, `not_installable`, `too_soon`, `locked`, `unauthorized`, `bad_request`, `failed`). An `/api/*` route this version does not know answers `404` and `{"error": "…"}`, never Admin's page.

**Signing in to Admin.** Signing in opens a 12 h session (`kyber_admin_session` cookie). With no Admin password (after `reset-password`), Admin writes an 8-character setup code to `setup-code.txt` and to its log; the sign-in screen asks for it with the new password (`POST /api/setup`), then the file is deleted. After five wrong passwords from the same address, Admin waits 30 s, then twice as long after each further failed attempt (10 min at most), answering `429` meanwhile; a successful sign-in resets the counter. argon2 checks (sign-in, setup, password change) never run more than two at a time: a burst from the network cannot exhaust memory.

**Stopping and restarting.** When the service stops (update, `Stop-Service`, shutdown), Admin first gives its displays and audio output back to the computer, then closes its connections; the service manager grants it 30 s. If the displays or the sound could not be given back (no Windows session open, for instance), the state file is kept and the next start tries again. An unreadable `kyber-admin.toml` is set aside (`kyber-admin.toml.invalide-…`) and Admin starts from default settings instead of not starting at all.

**KyberNow Link web client** (`/link/`; the former address `/ecran`, from 0.5.0 and earlier, redirects to it; sources in `server/web/src/link/`, “Open in the browser” entry on the Overview page). Open the computer from a browser, with nothing to install. It follows the shared screens and texts of the KyberNow Link apps ([docs/link-ui.en.md](../docs/link-ui.en.md)), with a single computer: the one serving the page.
- **Home screen** (`Home.svelte`): on the screen preview, the state (“Online”; “Searching…” while Kyber's engine loads; “Offline”, the reason and “Try again” if it does not load; “In session on …” when another device is connected), the name, the system (`os` from `GET /api/stream/info`), the display the session will ask for (“2560 × 1440 display at 120 Hz, sized for this screen”, or “The computer's own displays, as they are” without a virtual display), “Connect”, the Game, Desktop and Max profiles, and “Settings”. “Custom” shows when the format, bitrate or transport are chosen by hand; choosing a profile puts them back to Auto. An “Admin” link at the top.
- **Profiles** (`plan.ts`): the same rules as the apps' core (`apps/core/src/profile.rs`). Game: fast transport, 60 Mbit/s base. Desktop: reliable transport, sharp text (4:4:4), 90 Mbit/s. Max: fast transport, 4:4:4, 300 Mbit/s. 4:4:4 is only requested if this browser decodes it (otherwise a third more bitrate), H.264 adds half, the bitrate follows pixels per second (base for 4K at 60 Hz) and stays between 10 and 150 Mbit/s, which a browser decodes well.
- **Settings** (`Settings.svelte`, kept in the browser, `kybernow.ecran.prefs`): “Settings for {name}” (in French, « de » becomes « d' » before a vowel or an h, wherever the name follows it: `names.ts`), the profile, then Picture (virtual display, full screen, video format, bitrate), Sound, Controls (mouse or touch, shared clipboard, bar shortcut), Network (picture transport, the picture's path in this browser), Statistics and Station; at the bottom, “This app”: the language and, on touch devices, two tips (turn the phone, add the page to the Home Screen).
- **Statistics** (`Stats.svelte`, `FrameRuler.svelte`): this browser's last session, kept in `localStorage` (`kybernow.ecran.lastSession`) at the end of every session with at least 3 s of picture: median and 95th percentile of the per-second medians (like the apps' core, `latency.rs`), duration, date, resolution, refresh rate, format and bitrate; the frame ruler (0 to 20 ms, marks at 160, 120 and 60 Hz, band from the median to the 95th percentile). Then this computer (system, graphics card, the page's address, the fingerprint of Admin's certificate read from `GET /api/pairing`) and what this browser can do (decoding, 4:4:4, WebSocket, every key, screen size).
- **Station** (`StationPanel.svelte`, `station.svelte.ts`): version and update (`station` from `GET /api/stream/info`, read again every 8 s along with the current session), “Open Admin” (a link to `/`, same session), “Restart the Station” and “Update the Station” (`POST /api/stream/station/restart` and `/update` with Admin's session; a device in a session brings up “… anyway”, sent again with `force`), the account (the one from `GET /api/web/ticket`) and “Sign out of Admin”, which stands in for “Remove this computer”. Admin restarts with the Station and forgets its sessions: the page follows the return through `GET /api/session` every 2 s (no account needed, with the version: the new one, for an update), then reloads on the password screen with “The Station has restarted.” or “KyberNow Station … is installed.” (kept in `sessionStorage` across the reload). With no answer after 1 min 30: “The Station is taking a while to come back. Open Admin to find out more.”; back on the old version (30 s after its return), or never stopped within 10 min: “The update did not complete. Open Admin to find out more.” Without `station` (a Station from before 0.5.0), the section asks to update it from Admin.
- **Connecting and session** (`Session.svelte`): the computer's name and three steps (“Preparing the display”, “Connecting”, “First frames”), “Cancel”; then the picture alone, with no bar or figure over it. A failure before the first frame is titled “The connection failed”. Last resort: if Kyber does not connect (25 s), refuses the connection or does not start the picture while Admin answers, the page gives back the prepared display, restarts the Station without `force` (Admin refuses if another device is in a session: its session is never cut off), at most once every 10 min (`sessionStorage`), shows “The Station is restarting…” instead of the steps and waits for it to come back (1 min 30 at most). Since Admin has forgotten its sessions, the page reloads on the password screen, then connecting resumes on its own. If refused, the page shows the original failure; there is no last resort for a picture that is sent but does not arrive (browser or network) or for a refused token. The session bar opens on demand: with a mouse, when the pointer rests a quarter of a second against the top edge of the page (2 px at most), in a zone centered on the bar's width, with the page focused, the mouse not captured and no button held (a quick pass does not open it), through the top tab (220 px, touchable too; shown only when the gesture is possible: page in the foreground, pointer not captured, bar closed) or through `Ctrl + Alt + Shift`; on touch devices, through the top handle. It closes 0.4 s after the pointer leaves it, never while the Keys menu or Statistics are open; opened by finger or by the shortcut, with no pointer on it, it closes after 2.5 s. It offers: latency and Statistics, sound, Keys menu with Ctrl+Alt+Del, full screen with all keys in Chrome and Edge, “Disconnect”; on touch devices, a compact bar, trackpad or direct touch, and a row of keys above the device's keyboard.

How it works:
- **Account**: Admin's session (same password). `GET /api/web/ticket` (session required) signs an HS256 JWT (`aud` “kyber”, `sub`: the installation account, 12 h) with the key Kyber knows, set by `init` (see “Kyber's secrets”). The response is never cached (`Cache-Control: no-store`). The installation account (`install_account` in `kyber-admin.toml`) is the one created by `init`; an installation from before 0.2.6 records it at its first start (the first account of the list), so that removing or reordering accounts never signs the web client in under a paired device's account. The `/api/stream/*` routes also accept Admin's session: the web client prepares the display and sends its heartbeat like an app.
- **Heartbeat** (`heartbeat.ts`): every 5 s from a dedicated Worker built into the page (`blob:` URL, same origin and same isolation), whose timers are not slowed down in a hidden tab, plus an immediate one when the tab goes to the background; without a Worker, the page sends it itself. The end goes out with `keepalive` when the page closes (`pagehide`). The heartbeat and end bodies carry `device_id` (this browser's identifier, the one given to `prepare`); `backend.ts` accepts other fields. `end` in the heartbeat response (end requested from Admin, or another device taking over) ends the session with a message. A 401 from the heartbeat or the ticket (Admin sign-in expired) ends the session with a clear message, and going back to the home screen asks for the password again. The Kyber token is fetched again from `/api/web/ticket` whenever the engine reconnects (`reconnecting`, `authentication_required`) and every hour, then handed to the engine with `update_credentials()`.
- **Engine**: Kyber's `kyclient_wasm`, loaded from `/link/kyclient_wasm.js` (with `kyclient_wasm_bg.wasm`, `audio_worklet.js`, `spinlock.js`). Admin relays these files from the installed Kyber `/webclient/`: always the same version as the server. The page and these files are served with `Cross-Origin-Opener-Policy` and `Cross-Origin-Embedder-Policy` (shared memory for the sound).
- **Relay** (`kyber_proxy.rs`): the engine talks to kycontroller at the page's address, and kycontroller refuses other origins. So Admin relays `/session/login`, `/session/renew`, `/session/logout`, `/kymux/start_mux`, `/kymux/start_session`, `/ws` (WebSocket), `/capabilities`, `/enumerate_displays`, `/stop_streaming`, `/set_bitrate`, `/force_idr` and `/websocket/*` to kycontroller on this machine. In `/kymux/start_mux`, the image port announced by the engine (Admin's) is replaced by Kyber's. The relay does not expose kycontroller on Admin's port: it requires the **Admin session** (the engine, on the same origin, sends the cookie on `fetch` and on WebSockets; `401` without; the cookie is removed before Kyber, and the engine files are behind it too), refuses an `Origin` header that is not Admin itself (`403`; compared with `Host`, or with the request's authority over HTTP/2, which has no such header), only relays the paths above and simple names under `/websocket/` (nothing with `..`, `%2e`, `\` or `//`), **pins kycontroller's certificate** (SHA-256 fingerprint of the `[kycontroller] tls_cert` file, otherwise `kyber\kybertest_cert.pem`, read again if it changes; with no readable certificate, the relay is closed with `503`), caps relayed WebSockets at 8 at a time (`503` beyond), gives Kyber 15 s to accept the connection and answer (`502`), and keeps up to 4 HTTP connections open to kycontroller between requests instead of one TLS handshake per request. The image itself does not go through Admin: WebTransport on Kyber's port, verified by its certificate's fingerprint.
- **Image transport** (`plan.ts`, explained in Settings › Network): WebTransport on Kyber's port when possible; WebSocket (`/websocket/*`, relayed by Admin, a little more latency) on touch devices with the original engine (the page slips text and positions into the inputs connection, see below; the patched engine sends them itself, see “Patched engine”), in Safari and on iPhone and iPad (their WebTransport does not verify a certificate by its fingerprint), in Firefox (with the H.264 format in Auto, `device.ts`) and without WebTransport. Elsewhere, if the image does not come over WebTransport, the page switches to WebSocket (over WebSocket, the image gets 20 s, then the session fails with a message): the 12 s delay starts at the `streaming_started` event (Kyber accepted the session and started the image), not at connection time, which preparing the virtual display can delay by 8 s; from the connection on, a 25 s delay covers an image start that would never come. A control plane that does not connect within 25 s gives “Kyber is not responding”, without changing transport. Before creating another engine (switch, restart, new session), the page waits for the previous one's `stopped` event (3 s at most): never two engines, so never doubled inputs; a new display preparation also waits until the previous session's end has gone out. Each attempt (preparation, connection) carries a number: once outdated (end, Cancel, new attempt), it stops at its next step without creating an engine, and gives back the display it would have prepared.
- **Changes on the computer**: the engine relays the list of displays (`display_list_updated`). If the followed display disappears or changes size, the page restarts the image without reloading or disconnecting (`stop_streaming`, then on `streaming_stopped` a fresh canvas and `start_streaming`; Kyber also restarts the inputs, 1 to 2 s; with no answer within 5 s, the whole session starts over) and says so: “The computer's display changed”. An error in the image pipeline (`streamer_pipeline_event`, video) restarts the same way one second later, three times at most (the count goes back to zero after 30 s of image), then the session stops with a message; a sound error is only reported. `streaming_stopped` is never an end decided by the computer: Kyber only emits it at the client's request. The display targeted by positions (`displayId`) is learned again after each restart. The gamepads seen by the engine (`gamepad_plugged`, `gamepad_unplugged`) show in a chip in the bar.
- **Sound**: the browser may keep the sound suspended until a gesture has happened (Safari, iPhone, page opened without a click). After the first frame, the page asks `audio_try_resume()` every 200 ms (the engine creates its player at the first sound packet, sometimes a few seconds after the image); if it stays suspended, a “Tap for sound” chip calls `audio_resume()` within the gesture. Any click or key also retries.
- **Mouse**: the engine captures the pointer as soon as the computer hides its cursor, which Windows does constantly with no mouse plugged in. The page only allows capture in Game mode, or in Auto when Admin sees a full-screen game (`GET /api/stream/foreground`). `Ctrl + Alt + Shift` gives the mouse back and shows the bar; the tab at the top of the image shows it too. The engine draws the computer's pointer as the canvas cursor and sets `cursor: none` when the computer says it is hidden (always, with no mouse plugged in): outside capture, the page puts an arrow back. Outside capture too, the engine sends a relative move then the absolute position on every movement, both applied by the computer; the relative one (accelerated by Windows, lost outside the window) would shift the pointers: the page zeroes it, only the position counts, like the Mac app in desktop mode. Except when the computer's pointer is hidden (Windows hides it on the slightest keystroke): the engine then switches to relative mouse and only sends the move; since Windows only shows its pointer again on an absolute position, the page then sends the position itself on the inputs WebSocket connection (kynput packet `[2][display u32][x i16][y i16]`, display taken from the engine's positions or from `/enumerate_displays`); over WebTransport, where a whole message cannot be slipped into the stream, the move goes through as is. With the patched engine (except in Safari and on iPhone and iPad), the engine itself keeps sending the position outside capture: the page does not send it.
- **Touch**: the touch layer turns on as soon as there is a touch screen (`any-pointer: coarse`), also on an iPad with a Magic Keyboard: fingers touch directly, the mouse or trackpad stays the mouse (their clicks and wheel go through the guard) and the pointer takes the computer's one there. With the device keyboard open, the row of keys has a fixed height and sits right above the keyboard according to `visualViewport`; the image takes the rest, instead of half of the remaining space. During a session, closing the tab or quitting the browser (Ctrl+W, ⌘W, ⌘Q) asks for confirmation (`beforeunload`).
- **Device keyboard** (touch, `TypedText` in `touch.ts`): the hidden field that opens the keyboard sends text as kynput Unicode packets (`[10][code point u32]`, typed by Windows with `KEYEVENTF_UNICODE`) on the inputs WebSocket connection, which the page spots as soon as it is created: correct on a computer with an AZERTY layout, with capitals, accents and emoji. Text is read on `beforeinput` and `compositionend` (iOS, Android, dictation), never during a composition, and the field is only emptied outside of one. Enter, Backspace, Delete, arrows, Home, End, Page Up and Page Down, Escape and Tab stay keys (by their `code`, `DEVICE_KEYS`), as does text typed with sticky Ctrl, Alt or ⊞ (a shortcut, as QWERTY key codes). A real keyboard (iPad with a keyboard, Bluetooth keyboard) gives its keystrokes a `code`: the engine sends them, and the page does not send again the text they produce in the field. On touch devices, when the computer's pointer is hidden, the page also sends the finger's position on this connection (failing that, a relative move). With the patched engine (except in Safari and on iPhone and iPad), the field carries `data-kynput-text` and the engine types the text, over any connection: see “Patched engine”.
- **Clicks**: the engine listens to mouse buttons on the whole window, without looking at the target. A guard installed before it (`guard.ts`, in the capture phase on `window`) only lets through presses on the image (the canvas or the touch layer): a click in the session bar or on a touch button does not click on the computer. A button pressed on the image is released on the computer even if it is let go elsewhere. Touch buttons cancel `pointerdown`, which suppresses the browser's compatibility mouse events.
- **Wheel**: the engine ignores a wheel that counts in lines or pages (`deltaMode` other than pixel), which Firefox does. The guard converts it to pixels (40 px per line: the three lines of a Firefox notch make one notch on the computer, since the engine divides by 120; the window height per page) and sends it back to the canvas, like the wheel received by the touch layer, which covers the canvas. Two-finger scrolling goes out in whole notches (120 px).
- **Held keys and buttons**: the same guard tracks pressed keys (by `code`, which is what the engine reads) and buttons pressed on the image. When the window loses focus (`blur`, for example Alt+Tab or ⌘Tab), the tab is hidden or the captured mouse is given back, it sends a release for each one and forgets the touch sticky modifiers. If ⊞ or Alt were held, a Ctrl press goes first, so that Windows opens neither the Start menu nor the app's menu bar.

**Patched engine** (patches 0013 to 0015, see [docs/kyber-changes.en.md](../docs/kyber-changes.en.md)): with the overlay, `kyclient_wasm` is rebuilt by `server/kyber-patches/build.sh` and laid into Kyber's `webclient\`, so Admin relays it as it is. It reads by itself the text typed into a field marked `data-kynput-text` (Unicode packets, over WebTransport too), keeps sending absolute positions as long as the pointer is not locked (even when the computer hides its cursor), releases everything on `blur`, hidden tab and lost pointer lock, ignores gamepads without the "standard" mapping, and does not end the session on a decoding error if a keyframe comes within a second (the original engine ends it). The page recognizes this engine once it is loaded (`isFixedEngine()` in `engine.ts`): it exports nothing new, but imports from the browser the reading of `InputEvent.inputType` and `Element.hasAttribute` (the WebAssembly module's `__wbg_inputType_…` and `__wbg_hasAttribute_…` functions, used by its `beforeinput` listener), which the original engine lacks; the page looks for them in `WebAssembly.Module.imports()` of the module the engine's JS file keeps (`__wbindgen_wasm_module`). Unreadable or original engine: the page does the sending described above itself. Depending on the engine and the device (`engineInputs()` in `inputs.ts`):

| Device | Original engine | Patched engine |
|---|---|---|
| Computer (Chrome, Edge) | WebTransport; the page sends the position when the computer's pointer is hidden (over WebSocket only) | WebTransport; the page sends nothing, the engine keeps the position |
| Touch, except Safari and iOS (Android, Windows tablet) | WebSocket forced; the page sends text (Unicode) and the finger's position | WebTransport as on a computer; field marked `data-kynput-text`, the engine sends text and position |
| Firefox | WebSocket (the choice for this browser); the page sends | WebSocket; the engine sends |
| Safari, iPhone, iPad (every iOS browser, iPad presenting as a Mac included) | WebSocket; the page sends | same: WebSocket and the page sends |

Safari and iOS stay on WebSocket because their WebTransport does not verify a certificate by its fingerprint (`isWebKit` in `device.ts`); the page keeps its own sending there, whatever the engine. With the field marked, the engine reads the text on `document`, after the page: the page lets the text through (no `preventDefault`, no sending; except a paste whose text is only in `dataTransfer`, which the engine does not read) and the engine prevents it in the field or empties the field after a composition. The page keeps the keys (Enter, Backspace, arrows, Escape, Tab, through `preventDefault`, which the engine respects) and the text typed with sticky Ctrl, Alt or ⊞ (a shortcut, as keys: `preventDefault` on `beforeinput`, `stopPropagation` on `compositionend`, so that the engine does not type it too). Sorting out a real keyboard's keystrokes is then left to the engine (it prevents the text of the keys it sends). The diagnostics (`?diag`) tell which engine is loaded.

kycontroller also serves Kyber's original `/webclient/`, for troubleshooting.

Display, sound and pointer changes are made in the user's session by `kyber-admin.exe display-agent …`, launched by the service.

The `C:\ProgramData\KyberNow` folder is reserved to SYSTEM and Administrators: Admin reapplies its permissions at every start (`src/update/acl.rs`, see [server/installer/README.en.md](installer/README.en.md#permissions-of-cprogramdatakybernow)).

**Kyber's secrets** (`kyber_config.rs`). Program Files is readable by every account, and `kyber\kyber_config.toml` holds the (unsalted) SHA-256 hashes of the Kyber accounts' passwords. `kyber_config.toml`, kycontroller's certificate and key (`[kycontroller] tls_cert` and `tls_key`, otherwise `kybertest_cert.pem` and `kybertest_key.pem` next to it, produced by `cert-gen.exe`) and `kyber\avant-maj\` if it exists (a copy left by updates from before `kyber.prev`, which an update does not copy over) are reserved to SYSTEM and Administrators (Kyber runs as SYSTEM): applied by the installer, by `kyber-admin init`, at every Admin start and at every write of `kyber_config.toml` (the new file would otherwise inherit Program Files' permissions). An update copies `kyber\` into a new folder (applicator or `update.ps1`): the files get Program Files' permissions back until the new Admin starts, a few seconds later. The HS256 key of the web client's tokens is not in clear in `kyber_config.toml`: Kyber accepts `key = { file = … }` for HS256 too (`kycontroller/src/auth/jwt.rs`, `ConfigKey::File`, content read then trimmed), so `init` writes it to `C:\ProgramData\KyberNow\kyber-jwt.key` and `kyber_config.toml` only carries the path; an installation from before 0.2.6 (`key = { plain = … }`) is converted at Admin's first start, same key (Kyber reads it from the file at its next restart).

| `C:\ProgramData\KyberNow\devices.json`, `events.json` | known devices and last session, event feed of the Overview page |
| `C:\ProgramData\KyberNow\apps\` | catalogue of the user's apps (`catalogue.json`) and their icons (`icons\`), for “At session start” |
| `C:\ProgramData\KyberNow\setup-code.txt` | setup code, only while Admin has no password |
| `C:\ProgramData\KyberNow\update\relaunch-tray` | mark left by an update: Admin relaunches the icon in the user's session when it starts |
| `C:\ProgramData\KyberNow\display-watch\` | virtual display watch during a session (`run`: heartbeat, `state.json`: current mode and active displays) |
| `C:\ProgramData\KyberNow\foreground\` | full-screen watch during a session (`run`: heartbeat, `state.json`: last state) |
| `C:\ProgramData\KyberNow\kyber-admin.log` | the service's log, rotated at 5 MB (`.1` to `.4` kept, five files in all, all visible in System › Logs) |

Commands: `kyber-admin.exe service install|uninstall`, `kyber-admin.exe reset-password` (then restart the service), `kyber-admin.exe migrate [--dry-run]` (brings `kyber-admin.toml` to this version's format, also done at each start; see [docs/releases.en.md](../docs/releases.en.md#settings-migrations)), `kyber-admin.exe init …` (used by the installer), `kyber-admin.exe` alone to run in a console window (diagnosis).

## Developing on the Mac

```bash
cd server/web && npm run build                       # or npm run dev (proxies /api to Admin)
cd ../admin && cargo run -- --http --listen 127.0.0.1:9443 \
    --data-dir dev-data --kyber-dir dev-data/kyber    # copy a kyber_config.toml into dev-data/kyber
```

The local routes are tested with the token in `dev-data/local-token`: `curl -H "x-kyber-local: $(cat dev-data/local-token)" http://127.0.0.1:9443/api/local/state` (without the header: `403`). Outside Windows, the Kyber service, the virtual display and the sound are simulated, and Admin announces itself over Bonjour with `kyber=0` (the apps don't show it); `--announce-kyber` announces it with `kyber=1` to test adding and pairing from the apps (over HTTPS, without `--http`, and on `0.0.0.0` so that the Apple TV reaches it); for graphics cards, only NVML is tried (absent on the Mac); for Wake on LAN, a simulated Ethernet card (`wake` of `GET /api/stream/info`).

`cargo test` (in `server/admin`) also runs the virtual display state machine on the simulated driver (`display/mod.rs`, end of the file): display kept by the app against the automatic trigger, heartbeat from the owner, mode changed during the session with each policy (`follow`: announced once and kept; `restore`: put back, at most every 5 s, and right away by a `prepare` at the same mode; default policy from the setting), physical display turned back on (turned off after 2 s of stability, at most every 10 s, at the mode that fits the policy); and several displays: accepted and refused layouts, identifiers, order of the answer, display refused by the driver or not activated by Windows, main display required, policies on each display, physical display turned back on, recovery after a crash, single-display session unchanged. The watch moves one round per call to `watch_tick`, at the instant given by the test.

Web client against the Kyber on the test computer: run Admin over HTTPS (the engine always calls `https://`) with `KYBERNOW_KYBER_ADDR=192.168.1.100:30241` (Kyber's address and port on the test computer) and `KYBERNOW_KYBER_FINGERPRINT=sha256:…` (fingerprint of kycontroller's certificate on that computer, `openssl x509 -in kybertest_cert.pem -noout -fingerprint -sha256`; without it, the relay finds no certificate and answers `503`), then `npm run dev` in `server/web` (relay to `https://127.0.0.1:9448`) or open `https://localhost:<port>/link/`. The image can only arrive if the browser reaches Kyber at the page's address: on the Mac, the home screen and the settings can be checked; the session is tested on the computer itself.

## Updating a Station that is already installed

In one click: Admin's **Updates** page (or “Install version X…” in the icon's menu). Admin downloads the latest release of its channel published on GitHub, verifies its manifest's signature (`kybernow-release.json`, minisign), the package's size and checksum, and launches the applicator `kyber-admin update apply` (a detached copy of Admin, as SYSTEM): it verifies everything again, extracts the package under `C:\Program Files\KyberNow\.staging\`, switches the folders by renaming (the previous version stays in `kyber.prev`, `admin.prev`, `tray.prev`) and checks that Admin answers within 60 s with the new version, otherwise it puts the previous one back. `GET /api/session` gives Admin's version for that check. Details, manual update and publishing a release: [docs/releases.en.md](../docs/releases.en.md).

`server/installer/update.ps1` is for the manual path (`irm | iex`, `SHA256SUMS` checksum only) and for Admin versions older than 0.2.6. It replaces Admin, the icon and the Kyber overlay without reinstalling or changing the ports. It prepares `kyber.new`, `admin.new` and `tray.new`, switches by renaming (the previous version stays in `kyber.prev`, `admin.prev`, `tray.prev`), then checks that Admin answers within 60 s; otherwise it puts the previous version back. It also installs Steam's speakers if they are missing, adds the Bonjour firewall rule, puts back the services' permissions, the Start menu shortcuts and the display names, when launched by Admin asks it to relaunch the icon if it was running (`update\relaunch-tray`), and only keeps the two latest packages in `update\`. `server/installer/package-update.sh` builds its package (`dist/kybernow-update.zip`).
